The Agent Loop From Scratch

You're reading this lesson inside a system that just did something agent-like: it read a request, ran tools (file reads, writes, maybe a search), looked at what came back, and decided what to do next. Strip away the specific product and the branding, and every system like that is built from the same handful of parts: a system prompt, a set of tool schemas, and a loop that keeps calling the model until the model says it's done. This lesson builds that loop from nothing, in pseudocode, so the rest of the course has a precise, un-mysterious thing to refer back to.

The system prompt: instructions the user never sees

Every model call in an agent system carries two very different kinds of text. One is the system prompt — standing instructions written by whoever built the harness, describing the agent's role, its available tools, and the rules it should follow. It isn't sent once and remembered; it's resent, verbatim, as part of every single call, because — as the next section makes precise — the model has no memory of its own between calls. The other kind of text is the ordinary conversation: what the user asked for, and what happened as a result of each tool call so far.

The system prompt is where the harness author encodes things the model has no other way of knowing: what tools exist and roughly when to use them, what "done" looks like for this kind of task, any constraints ("never delete a file without confirming," "always run tests before declaring success"). Get this vague, and everything downstream gets harder to reason about — a concern this whole course keeps coming back to, starting with tool descriptions in the next lesson.

Tool schemas: a menu the model can actually order from

A model can't literally reach out and touch a file system, run a command, or query a database — the harness code around it can. A tool schema is the structured description that tells the model what actions the harness is willing to perform on its behalf, and exactly what arguments each one needs. In practice this is JSON: a name, a natural-language description, and a parameter schema with types.

{
  "name": "run_tests",
  "description": "Runs the project's test suite and returns pass/fail per test.",
  "parameters": {
    "type": "object",
    "properties": {
      "path": { "type": "string", "description": "Test file or directory to run." }
    },
    "required": ["path"]
  }
}

When the model decides a tool is worth calling, it doesn't run any code itself — it emits a structured request (this tool name, these arguments) as its output for that turn. The harness is the thing that actually validates those arguments against the schema and executes something real. That division of labor — model proposes, harness disposes — is the whole reason a tool schema needs to exist at all: it's the contract the two sides agree to communicate through. Lesson 2 is entirely about designing that contract well.

The read-act-observe loop

Put the system prompt, the tool schemas, and a growing conversation transcript together, and you get the loop that actually makes something feel like an "agent" rather than a single question-answer exchange:

SYSTEM_PROMPT = "You are a coding assistant with access to the tools below.
                 Call a tool by name with JSON arguments matching its schema.
                 When you are done, respond with plain text and no tool call."

TOOLS = [read_file_schema, edit_file_schema, run_tests_schema]

messages = [ {role: "system", content: SYSTEM_PROMPT},
             {role: "user",   content: "Fix the failing test in auth.rs"} ]

loop:
    response = call_model(messages, tools=TOOLS)            # READ — the model reads the transcript so far

    if response.tool_call is None:
        return response.text                                # done: no tool call this turn, stop the loop

    result = execute(response.tool_call.name,                # ACT — the harness runs real code, not the model
                      response.tool_call.arguments)

    messages.append({role: "assistant", tool_call: response.tool_call})
    messages.append({role: "tool", tool_call_id: response.tool_call.id,
                      content: result})                       # OBSERVE — the result re-enters the transcript
    # loop repeats — the model "reads" its own last action next iteration
The agent is the loop, not the model. A single call to the model is close to a stateless function: transcript in, one message out. There is no persistent "self" living inside the model between calls. Everything that makes a system feel like an agent — remembering what it just did, deciding to keep going, knowing when to stop — is ordinary control-flow code sitting outside the model, written by whoever built the harness. The three-letter acronym (READ / ACT / OBSERVE) names three steps of one loop iteration, not three different components.

Three iterations of this loop, concretely: READ — the model sees "fix the failing test," has no file contents yet, and calls read_file("auth.rs"). ACT — the harness actually opens the file and reads it. OBSERVE — the file's contents come back as a tool message, appended to the transcript. The next iteration's READ sees that file content for the first time and can now propose an edit. Nothing about the model changed between iterations — only the transcript it's conditioned on grew.

The model has no memory between calls

This is worth stating as sharply as possible, because almost every later topic in this course — context and memory management, failure diagnosis — depends on taking it literally: if something happened three tool calls ago and its result isn't sitting in messages right now, it is exactly as if it never happened, from the model's point of view. There's no side channel, no persistent scratch space the model quietly keeps for itself between one call_model() invocation and the next. Whatever the harness didn't put in the transcript, the model cannot know.

Why naive loops don't stop

A loop needs an explicit reason to stop. If nothing in the system prompt or the harness logic ever tells the model "you are done, stop calling tools, respond in plain text," a model that's inclined to keep being helpful will happily keep calling tools well past the point of any use — right up until it errors out, exhausts a step budget, or the user gives up watching. A termination condition (a "you're done" instruction, a max-iteration cap, a plain-text-response detector like the pseudocode's if response.tool_call is None) is not optional polish. It's a required part of the loop, exactly as required as the loop itself.

Two more naive-loop failure modes worth naming now, because they resurface as concrete case studies in lesson 4's worked example: a model can propose a tool call the harness has no schema for (or with arguments that don't match the schema), and a model can receive a tool result and then act as if it hadn't — repeating the same call, or continuing on a plan the observation should have changed. Neither is a mystery once you can see the loop; both are exactly the kind of bug this course spends real time on.

Practice before next lesson

Pick one tool you actually use often in your own work (a linter, a database query, a deploy script) and write its schema as JSON, following the run_tests shape above. Then trace three iterations of read-act-observe by hand for a plausible task using that tool: what does the model see at each READ, what does the harness actually do at each ACT, and what specific new fact does each OBSERVE add that the model didn't have before? Finally, write the exact condition that should make the loop stop.
