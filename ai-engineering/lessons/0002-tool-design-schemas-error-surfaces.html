Tool Design

Lesson 1 established that the model never touches the real world directly — it proposes a tool call, and the harness is the thing that actually acts. Everything the model knows about what a tool does, and everything it has to go on after calling it, comes from two pieces of text you write: the tool's description, and the shape of what it returns. Get those wrong and the model isn't being "dumb" when it misuses a tool — it's making a reasonable guess from an underspecified contract. This lesson is about writing that contract well.

Anatomy of a tool definition

A tool definition communicates four things, only two of which are usually written down carefully:

  • Name — usually gets attention; a specific, verb-first name (search_codebase) already does real work over a vague one (search).
  • Description — a natural-language sentence or two, read by the model on every call where this tool is available. This is the part most often written lazily, and the part this lesson focuses on.
  • Parameter schema — types and required/optional fields, usually written carefully because omitting it causes an obvious, immediate error.
  • Return shape — almost never specified in the schema itself, and almost never thought about until something goes wrong. The next section is entirely about this one.

Before and after: the same tool, two descriptions

Here is a tool description that is technically valid JSON and technically documents a real tool — and will still cause an agent to misuse it:

{
  "name": "search",
  "description": "searches",
  "parameters": {
    "query": { "type": "string" }
  }
}

Nothing here tells the model what's being searched, what it returns, how much it returns, or when to reach for this tool instead of some other one. A model conditioned on this schema has to guess — and a guess baked into a tool call becomes a real action, not a harmless misunderstanding. Compare it with a version that answers those questions up front:

{
  "name": "search_codebase",
  "description": "Full-text search across tracked source files in the repository. Returns up to 50 matching lines with file path and line number. Does not search binary files, node_modules, or .git. Use this before assuming a symbol doesn't exist in the codebase.",
  "parameters": {
    "type": "object",
    "properties": {
      "query":     { "type": "string", "description": "Literal substring or regex pattern to search for." },
      "path_glob": { "type": "string", "description": "Optional glob to restrict the search, e.g. '**/*.rs'." }
    },
    "required": ["query"]
  }
}

Same underlying tool, radically different odds of being called correctly. The good version states scope ("tracked source files"), a hard limit on output size ("up to 50 matching lines" — which also protects the context window, the subject of the next lesson), an explicit exclusion ("does not search binary files… "), and a cue for when to reach for it at all.

Error surfaces: what a tool says when it fails

The error surface of a tool is the shape and content of what it returns when something goes wrong — not just whether it failed, but what the caller should do about it. This matters more for an agent than for a human caller, because a human reading a stack trace brings outside context (they've seen this error before, they can search for it, they can ask a colleague); the model has only what's in the tool result and the rest of the transcript.

// Bad — a raw exception leaks straight through
Traceback (most recent call last):
  File "tools.py", line 42, in read_file
    with open(path) as f: ...
FileNotFoundError: [Errno 2] No such file or directory: 'fpp.txt'

// Good — a structured, actionable error
{
  "ok": false,
  "error": "file_not_found",
  "message": "No file at 'fpp.txt'. Closest match in this directory: 'foo.txt'."
}

The bad version isn't wrong, exactly — it's true, and a human debugging by hand would find it useful. But it wasn't written for a reader that only gets one shot at the OBSERVE step of the read-act-observe loop before deciding what to do next. The good version gives the model a machine-checkable failure kind (file_not_found) it can branch on, plus a concrete, actionable next step (the suggested filename) — turning a dead end into a fact the model can actually use.

A tool description is a contract with a reader who can't ask a clarifying question. The model reads the schema once per call and has to act on it immediately — it can't message you asking "does path mean absolute or relative?" Whatever's ambiguous in the description is a decision the model has to make on its own, silently, and you won't find out which way it guessed until something breaks.
Ambiguity that's harmless to a human reader can be catastrophic to a model. A human skimming "amount": {"type": "number"} on a payment tool infers a lot from surrounding context, house conventions, or just asking someone. A model conditions only on the literal schema and description text in front of it, plus whatever else happens to be in the transcript — nothing else. Cents or dollars? Inclusive or exclusive of tax? Any assumption you didn't write down is an assumption the model is free to guess wrong, and a wrong guess here isn't a lint warning — it's a real transaction.

Check your understanding

1. Why does a vague tool description like "searches" tend to cause misuse, even though a human reading the function name might correctly guess its behavior?

2. What's the main benefit of returning a structured error ({"ok": false, "error": "file_not_found", ...}) instead of letting a raw stack trace reach the model?

3. Why should a tool's description state what it does not do, not just what it does — as in "does not search binary files, node_modules, or .git"?

4. Beyond documentation, what functional job does a parameter's JSON Schema type (e.g. "type": "string") do inside the loop from lesson 1?

Practice before next lesson

Take a tool you use often in your own work — or invent one, like run_lint — and write two versions of its schema: one intentionally vague (name, one-word description, untyped parameters), and one following the name/scope/limits/when-to-use pattern from this lesson. Then imagine you're the model with no other context beyond the schema text itself: which version would you trust to call correctly on the first try, and specifically what question would the vague version leave you guessing at?
