Context & Memory

Every OBSERVE step appends something to the transcript. A long-running agent — one that reads files, runs commands, and calls tools dozens of times in a row — can generate a transcript that's enormous by the time it's actually done. But transcripts don't grow for free, and this lesson is about the fixed budget they grow into, and the three main strategies for managing what happens when they hit it.

The context window: your only working memory

The context window is the fixed token budget for a single model call. The system prompt, the entire conversation and tool-call history, the tool schemas themselves, and the model's own response all draw from this one, per-call budget. Nothing outside it exists to the model for that call — no matter how important it was three tool calls ago.

A useful analogy for a systems background: the context window behaves like a CPU's register file or L1 cache, not like RAM or disk. It's small, and everything in it is directly usable by the model on this call — but anything you want the model to reason about has to be loaded into that window for this specific call, the same way data has to be paged into cache before a CPU instruction can touch it. "It's in the conversation somewhere" isn't the same as "it's in the window right now" if the harness already dropped or compressed it.

Bigger isn't free: context rot

More context is not free, even when it's all correct. As a transcript grows, the model's effective ability to make use of any one piece of information tends to degrade — not just the obvious costs of latency and dollars per token, but retrieval accuracy itself, especially for facts sitting in the middle of a long transcript rather than near the very start or the very end. This effect is sometimes called context rot or the "lost in the middle" problem. It means stuffing everything into context isn't a safe default — it actively works against the thing you're trying to protect.

The naive strategy: truncation

The simplest way to stay under budget: when the window fills up, drop the oldest messages. It's free — no extra model call, no infrastructure — and it's blind. Truncation has no idea whether the oldest message was idle small talk or the one tool result the rest of the task depends on; it drops whatever is oldest, unconditionally.

Summarization: compress the past into a shorter present

Instead of dropping old messages outright, summarization periodically replaces a run of them with a single, shorter, model-generated message that preserves the gist:

if tokens_used(messages) > SUMMARIZE_THRESHOLD:
    old, recent = messages[:-KEEP_RECENT], messages[-KEEP_RECENT:]
    summary = call_model(SUMMARIZE_PROMPT, old)   # a call whose only job is
                                                    # compression, not task progress
    messages = [system_prompt, summary_message(summary)] + recent

This trades a real cost — an extra model call, plus the risk that the summarization prompt itself drops something that mattered — for controlled loss instead of truncation's arbitrary loss: you're choosing, deliberately, what's likely to still matter. In a long-running coding-agent session specifically, this technique is often called compaction: summarizing to keep a session alive past what would otherwise be a hard context limit, typically preserving things like file paths touched and decisions made while dropping raw tool output that's already been acted on and won't be needed verbatim again.

Retrieval: index it, and fetch it back on demand

The third strategy doesn't try to keep everything — or a lossy summary of everything — resident in the window at once. Instead, information is stored externally (a file, a vector index, a database), and the harness pulls back only the specific pieces relevant to the current step, via a dedicated retrieval tool call, exactly when they're needed. This is retrieval-augmented generation (RAG) applied to an agent's own working history, not just to external documents — the same idea, turned inward.

None of these three strategies is strictly better. They trade differently along cost, precision, and infrastructure. Truncation is free but arbitrarily lossy. Summarization costs a call and loses detail in a controlled way — good for "gist" material, bad when an exact number or an exact line of code needs to survive intact. Retrieval scales to huge histories with high precision when it hits, but requires building and querying an index, and adds a new failure mode of its own: the retrieval step can simply miss the right thing. A production agent typically runs more than one of these at once — summarizing resolved small talk while retrieving exact file contents on demand rather than pinning every file it's ever touched in the window.

Practice before next lesson

Sort what happened into three buckets: things safe to summarize down to their gist, things you'd want retrievable exactly on demand, and things safe to just let fall off the end via plain truncation. Notice how few things end up in that third bucket once you think it through carefully — which is itself the point of this lesson.
