Failure Modes

The first three lessons gave you three places a bug can live: the system prompt and loop logic, the tool definitions and their error surfaces, and the memory/context strategy. There's a fourth suspect — the underlying model's actual capability — but it should be the last one you reach for, not the first. This lesson turns those four suspects into a discipline: a way to diagnose a broken agent instead of guessing at it.

The four places a bug can hide

  1. Prompt — the instructions are missing, ambiguous, or contradictory (e.g. never states what "done" means for this task).
  2. Tools — the schema is under-described, the parameters are ambiguous, or the error surface doesn't return enough for the model to act on.
  3. Memory / context — a fact the model needed got truncated, garbled by a lossy summary, or never got retrieved in the first place.
  4. Model — the underlying model genuinely lacks the capability the task requires.

The order matters. The first three are things you wrote and can inspect directly — you can read the exact prompt text, the exact schema, the exact transcript the model saw. The fourth is the one thing you can't directly edit your way out of. Cheaper, more inspectable causes should be ruled out first, precisely because they're the ones you have the power to fix immediately if they turn out to be the problem.

Isolate one variable at a time

Change one layer, then test — not all three at once. The prompt, the tool definitions, and the memory strategy can each be changed independently. If you rewrite the system prompt, loosen a tool's schema, and switch from truncation to summarization all in the same attempt, and the failure goes away — you now know something fixed it, but not which of the three actually did. Worse, if it doesn't go away, you've burned an attempt without learning which hypotheses to rule out. This is the same discipline as binary-search debugging in ordinary software: change one thing, observe, then decide the next change.

Worked example: diagnose this broken agent

A coding agent is asked to fix a failing test in auth.rs. It has three tools: read_file, edit_file, and run_tests. Here's what happens: it reads the file, makes a plausible-looking edit, runs the tests, gets back {"passed": false}, edits a completely different, unrelated function, runs the tests again, gets {"passed": false} again, and keeps cycling like this — never converging, never explaining what it thinks is wrong.

Walk the checklist in order:

  • Prompt — the instructions clearly state the goal ("fix the failing test") and the tool to verify it with. Not obviously the cause; move on.
  • Tools — look at what run_tests actually returns:
// What run_tests returns today
{ "passed": false }

// What it should return
{
  "passed": false,
  "failing_test": "auth::tests::rejects_expired_token",
  "stderr": "assertion failed: token.is_expired() == true, got false — at auth.rs:118"
}

There it is. The tool's error surface is giving the model exactly one bit of information — false — on every failed attempt. Per lesson 1's OBSERVE step, that single bit is the entire new information the model gets each iteration. With nothing pointing at which assertion failed or why, the model has no way to converge — it isn't malfunctioning, it's doing the best it can with an OBSERVE step that was never given anything to observe. Fixing the tool's return shape, not the prompt, is what actually resolves this.

Memory and model were never the issue here — but notice you didn't need to touch either of them to find that out. You checked the cheapest, most inspectable layers first, in order, and stopped as soon as one produced a concrete, verifiable explanation.

Root cause vs. symptom

A broken agent system is a diagnosis problem before it's a prompt-engineering problem. The most common mistake in practice is treating every failure as "needs more instructions in the system prompt" — bolting on a new sentence like "make sure to actually read the test failure output carefully" every time something goes wrong, without ever checking whether the tool was giving the model anything to read in the first place. That's patching a symptom, not fixing a root cause.
Symptom-patching has a real cost, not just an aesthetic one. Every extra prompt sentence added to work around a suspected tool or memory bug is text that now has to be sent — and attended to — on every single call, forever, competing for the same context window budget from lesson 3. A system prompt that's accreted forty special-case instructions over months of symptom-patching is both harder to debug later and actively works against the model, via the same context rot effect covered last lesson.
