Orchestration Patterns: Planner/Worker and Subagent Delegation

So far everything has been one loop: one read-act-observe loop, one transcript, one context window, kept healthy by compaction and debugged with the four-layer diagnosis. This lesson adds a second loop. A subagent is nothing exotic: it is one tool call whose ACT step runs another loop. The real question is when splitting work across agents beats one agent, what the split costs, and how to write the brief that crosses the boundary.

Workflow vs. agent: who picks the next step?

Anthropic's Building Effective Agents draws the line. A workflow is a system where “LLMs and tools are orchestrated through predefined code paths”. An agent is one where “LLMs dynamically direct their own processes and tool usage”. To tell them apart, ask one question: is the next step chosen by code you wrote, or by the model at run time?

Its catalogue of workflows, in rising complexity: prompt chaining (a fixed sequence), routing (classify, then dispatch), parallelization (simultaneous calls combined by code: sectioning into independent subtasks, or voting on one task), orchestrator-workers (a model splits the task at run time and combines the results), and evaluator-optimizer (generate, critique, repeat). It files orchestrator-workers under workflows even though a model picks the subtasks, because your code still fixes the plan, fan-out, synthesize shape: the line is a spectrum, not a switch. The read-act-observe loop, where the model picks every step, is the far end: a full agent.

Use the least autonomy that does the job. “Agentic systems often trade latency and cost for better task performance, and you should consider when this tradeoff makes sense.” If you can write the subtasks down before you see the input, write them down in code.

A subagent is a tool call whose ACT step is another loop

To the parent, delegation is one more tool schema:

{
  "name": "spawn_subagent",
  "description": "Delegate a self-contained subtask to a fresh agent. It sees ONLY this brief, not this conversation, and returns only its final answer.",
  "parameters": {
    "type": "object",
    "properties": {
      "brief": { "type": "string", "description": "Objective, output format, tools and sources, boundaries." },
      "tools": { "type": "array", "items": { "type": "string" } }
    },
    "required": ["brief", "tools"]
  }
}

The harness implements it by calling the loop you already have, recursively:

def run_agent(system_prompt, task, tools, max_steps):
    messages = [ {role: "system", content: system_prompt},
                 {role: "user",   content: task} ]          # a FRESH transcript
    for step in range(max_steps):                           # its own termination condition
        response = call_model(messages, tools=tools)        # READ
        if response.tool_call is None:
            return response.text                            # the only thing that crosses back
        result = execute(response.tool_call.name,           # ACT (may spawn again: recursion)
                         response.tool_call.arguments)
        messages.append({role: "assistant", tool_call: response.tool_call})
        messages.append({role: "tool", tool_call_id: response.tool_call.id,
                         content: result})                  # OBSERVE
    return "stopped: step budget exhausted"

def execute(name, args):
    if name == "spawn_subagent":                            # this ACT step is a whole loop
        return run_agent(WORKER_PROMPT, args.brief, pick(TOOLS, args.tools), max_steps=15)
    ...                                                     # read_file, edit_file, run_tests

Read it as a C programmer would. The worker's messages is a local: created fresh, discarded like a stack frame when run_agent returns. Only the return value reaches the parent. Because every model call is stateless, the worker knows only what its brief says and the parent learns only what the worker returns. A fresh subagent is closer to posix_spawn() plus waitpid() than to a thread: a new process with no shared address space, the brief its argv, the returned text its stdout. It also needs its own termination condition (here a step cap), or one runaway worker stalls the tree.

The harness you work in documents the same shape, as behaviour rather than implementation. As of October 2026, Claude Code's subagent docs say each subagent “runs in its own context window with a custom system prompt, specific tool access, and independent permissions”, returns only a summary, and can nest up to three layers below the main conversation by default. A fork, closer to a bare fork(), inherits the whole conversation: it “drops the input isolation” but still returns only its final result. A per-worker tool list is least privilege, enforced in the guardrails lesson.

Orchestrator-worker: plan, fan out, synthesize

Give a lead agent spawn_subagent and you get the orchestrator-worker (planner/worker) pattern. The lead decomposes the task, workers run (usually in parallel), each worker returns a condensed result, and the lead combines them. What separates this pattern from sectioning is where the subtask list lives:

# Sectioning (a fixed workflow): the subtasks live in YOUR code
checks  = [LINT_PROMPT, LICENSE_PROMPT, CHANGELOG_PROMPT]
results = parallel_map(lambda p: call_model(p, pr_diff), checks)
report  = merge(results)                                    # combined by code

# Orchestrator-worker: the subtasks live in the MODEL's output
plan    = call_model(PLANNER_PROMPT, user_task)             # 2 briefs, or 7, or 12
results = parallel_map(lambda b: run_agent(WORKER_PROMPT, b.brief,
                                           pick(TOOLS, b.tools), max_steps=15),
                       plan.briefs)                         # returns when the SLOWEST worker does
answer  = call_model(SYNTHESIS_PROMPT, user_task, results)  # combined by a model

In Building Effective Agents' words, the “subtasks aren't pre-defined, but determined by the orchestrator based on the specific input.” (A real lead is itself a loop issuing several spawn_subagent calls per turn; the sketch flattens that.)

Anthropic's write-up of its Research feature (June 2025) is a first-hand account of this pattern in production. The lead spins up 3–5 subagents in parallel, and because agents misjudged effort (early versions made errors like “spawning 50 subagents for simple queries”), its prompt carries scaling rules: one agent and 3–10 tool calls for simple fact-finding, more than 10 subagents for complex research.

Why split: context isolation, breadth, specialization

1. Context isolation. A worker can churn through a verbose search, a long log or a large file in its own window and hand back only the conclusion. Anthropic's context-engineering guide describes subagents that use “tens of thousands of tokens or more” but return “a condensed, distilled summary of its work (often 1,000-2,000 tokens)”. It lists this beside compaction and note-taking: delegation is a context strategy, the worker's return is a summarization step with the same controlled loss, and the lead's short transcript resists context rot. That alone can justify a split, even with one worker and no parallelism.

Illustrative: three workers each read about 40k tokens and return 1.5k. The lead's window grows by 4.5k instead of 120k (about 27× less), but all 120k are still read and billed, in the workers' windows instead of the lead's, plus the briefs, the returns and the lead's own calls. (Strictly more than 120k: each worker resends its growing transcript on every model call.) Isolation moves tokens out of the lead's window; it does not make them free.

2. Breadth-first parallelism. Independent directions run at once. In the Research system, parallel subagents plus parallel tool calls “cut research time by up to 90% for complex queries”, and an Opus 4 lead with Sonnet 4 workers beat single-agent Opus 4 by 90.2% on Anthropic's internal research eval.

3. Specialization. Each worker gets a narrower prompt and tool list, which the Research write-up calls “separation of concerns”.

What splitting costs: the token multiplier

chat 1×single agent ≈4×multi-agent ≈15×tokens, Anthropic Research, 2025

The Research write-up reports that “agents typically use about 4× more tokens than chat interactions, and multi-agent systems use about 15× more tokens than chats.” On BrowseComp, “token usage by itself explains 80% of the variance” in performance; such systems “work mainly because they help spend enough tokens to solve the problem.” Splitting buys capacity and breadth, not free intelligence. Dividing the averages gives a crude 15 ÷ 4 ≈ 3.75× a single agent's spend (crude, because the two averages were not measured on the same tasks), and only a valuable task repays it. The other costs:

  • Waiting. The Research lead waits for each batch, so “the entire system can be blocked while waiting for a single subagent to finish searching.” Illustrative: workers taking 40, 55, 90 and 300 s finish in 300 s, a 1.6× speedup over running them in sequence (485 s), not 4×. That is fan-out tail latency, priced in the production lesson.
  • Duplication. Given the vague brief “research the semiconductor shortage”, one Research subagent explored the 2021 automotive chip crisis while two others duplicated each other on current 2025 supply chains.
  • New failure modes. The MAST study (Cemri et al., 2025) annotated 1,600+ traces from 7 multi-agent frameworks against a taxonomy of 14 failure modes, one whole category of them inter-agent misalignment. Finding them needs each subagent as its own span in an agent trace.
Actions carry implicit decisions. Cognition's Don't Build Multi-Agents (June 2025) names the cost that hits coding hardest: “Actions carry implicit decisions, and conflicting decisions carry bad results.” Split “build a Flappy Bird clone” between a background worker and a bird worker. Even when both see the full task, the bird and the background can come back in completely different visual styles, because neither saw what the other was doing. Every edit settles something nobody wrote down (error type, naming, edge cases), and parallel workers settle it differently. The post's default is a single-threaded agent that compresses its history, which is compaction again. Anthropic agrees: “most coding tasks involve fewer truly parallelizable tasks than research”.

As of October 2026 the two positions sit closer together. Cognition's April 2026 follow-up reports multi-agent setups that work when “writes stay single-threaded and the additional agents contribute intelligence rather than actions”. A controlled study from Google Research, DeepMind and MIT (Kim et al., preprint revised April 2026) found performance relative to a single agent ranged “from +80.8% on decomposable financial reasoning to -70.0% on sequential planning”. Whether a split beats one agent on your task is empirical, and a capability eval is how you find out.

The split decision, in three questions.
  1. Can you list the subtasks before seeing the input? Use a fixed workflow; no model needs to plan.
  2. Do the subtasks share decisions or write the same state? Keep one agent (plus compaction); delegate only read-only side tasks whose conclusion is all you need.
  3. Is the work breadth-first, the subtask count input-dependent, and the result worth ~15× chat tokens? Use orchestrator-workers.

The delegation brief is a contract

The Research write-up says each worker “needs an objective, an output format, guidance on the tools and sources to use, and clear task boundaries.” A brief is a tool description pointed the other way. One model writes it for another, and it is still a contract with a reader who can't ask a clarifying question. In the running example, the lead suspects the expiry check in auth.rs and hands off a read-only investigation:

{
  "objective": "Find why auth::tests::rejects_expired_token fails. Locate where token expiry is computed and every caller of Token::is_expired in crates/auth/. Lead's hypothesis: the comparison at auth.rs:118 uses the wrong clock.",
  "output_format": {
    "findings":   [{ "file": "crates/auth/src/auth.rs", "line": 118, "role": "computes | calls | tests", "note": "one sentence" }],
    "verdict":    "confirmed | refuted | unclear, plus at most two sentences citing file:line",
    "max_tokens": 1500
  },
  "tools": ["read_file", "search_codebase"],
  "boundaries": "Read only: do not edit files or run tests. Stay inside crates/auth/. Stop after 15 tool calls, or once a file:line confirms or refutes the hypothesis."
}

Each field closes a known failure. The objective carries the lead's hypothesis, because the worker cannot see the lead's transcript. The output format is the worker's error surface: a bare "done" gives the lead nothing to observe, and 30k tokens of raw grep output undoes the isolation you split for. The verdict lets the worker refute the hypothesis instead of hunting for confirmation. The boundaries prevent duplication, keep writes with the lead, and set a stop condition. When workers still duplicate each other, the four-layer diagnosis says check the prompt layer before the model: Anthropic saw exactly this from vague briefs.

A live example: the second half of this course (lessons 5–8) was written by parallel writer agents from one planner's plan, and none saw another's draft. Each writer got its scope, an out-of-scope list and fixed anchor ids such as #delegation-brief, so the guardrails lesson could link here before this page existed. Those fixed fields settled implicit decisions in advance. A reviewer agent then checked each lesson in a clean context, and edits to shared files (topic index, search index) wait for one central integration pass: many writers on separate files, one writer on shared state.

Check your understanding

1. A lead agent has read auth.rs and suspects the expiry check. It spawns a fresh (non-fork) subagent whose brief says only “list the callers of Token::is_expired.” What does the worker know about the lead’s hypothesis?

2. In Anthropic’s Research data, multi-agent runs used about 15× the tokens of chat, and token usage alone explained 80% of the variance in performance. Which reading follows?

3. A lead splits “add a settings page” between a form-UI worker and an API-handler worker, running in parallel. Each passes its own tests, but their field names disagree. What is the best fix?

4. Four workers each read about 30k tokens and return 2k-token summaries. Compared with one agent reading all 120k tokens itself, what does the split save?

Practice before next lesson

Write the JSON delegation brief that card 1’s lead would send to one competitor-pricing worker: all four fields, a return shape the lead can merge straight into the table, a boundary that stops two workers covering the same competitor, and a stop condition. Then budget it: if one agent would spend T tokens on the whole job, the crude 15 ÷ 4 ratio of the published averages suggests roughly 3.75T for the split. Which numbers in your own brief (worker count, sources per worker) would push that up or down, and what would make the comparison table worth it?
