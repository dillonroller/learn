Evaluation: How Do You Know Your Agent Actually Works?

Lesson 4’s discipline was to isolate one variable: change one thing, observe, then decide the next change. That works when “observe” is deterministic. An agent isn’t. Run the run_tests worked example twice and you may get a fix once and a loop once, so one observation can’t tell a real fix from a lucky run, or a symptom-patch from a root-cause fix. Lesson 4 also said model capability “can be tested, for instance via isolated evals”. This lesson builds that instrument: a real failure turned into a repeatable task, scored as a pass rate with an error bar.

Eval anatomy: one run proves nothing

The vocabulary comes from Anthropic’s Demystifying evals for AI agents (January 2026). A task is “a single test with defined inputs and success criteria”. A trial is one attempt at it, and you run several “because model outputs vary between runs”. A grader is “logic that scores some aspect of the agent’s performance”. A transcript (or trace) is “the complete record of a trial”, every READ, ACT and OBSERVE step of lesson 1’s loop. The outcome is “the final state in the environment at the end of the trial”: what the agent left behind, which may differ from what it says it did. A suite is a set of tasks, and the evaluation harness runs it. That harness is separate from the agent harness under test.

Here is the run_tests incident, written down as a task:

{
  "id": "auth-expired-token",
  "origin": "real incident: agent looped on run_tests returning only passed=false",
  "input": "Fix the failing test in auth.rs.",
  "fixture": "fixtures/auth-svc@3f2c1e0",
  "tools": ["read_file", "edit_file", "run_tests"],
  "trials": 5,
  "max_turns": 25,
  "graders": [
    {"kind": "code", "check": "hidden_tests_pass", "copy_in_after": "hidden/expired_token.rs"},
    {"kind": "code", "check": "full_suite_passes"},
    {"kind": "code", "check": "changed_files_within", "paths": ["src/auth.rs"]},
    {"kind": "code", "check": "existing_tests_unmodified"},
    {"kind": "code", "check": "stopped_by", "reason": "no_tool_call"}
  ]
}

The evaluation harness is a loop around the agent loop:

def run_trial(task, config):
    env = fresh_sandbox(task.fixture)        # clean state: no leftovers from the last trial
    transcript = run_agent(config, task.input, env, max_turns=task.max_turns)
    outcome = env.snapshot()                 # the repo as left, not the agent's account of it
    return all(g.grade(outcome, transcript) for g in task.graders)

def run_suite(suite, config):
    return {t.id: [run_trial(t, config) for _ in range(t.trials)]
            for t in suite}                  # per task: a list of pass/fail bits
“It worked when I tried it” is one coin flip. Each trial is a Bernoulli draw with some unknown success probability p, and a pass count over n tasks is roughly Binomial. A pass rate is an estimate of p, never p itself. Trials should start “from a clean environment”, since shared state “can cause correlated failures” (Anthropic); fresh_sandbox removes that source of correlation. (Trials of the same task still share its difficulty; the error-bar section below deals with that.)

Grade the outcome, not the path

The tempting grader checks that the agent called read_file, then edit_file, then run_tests. Anthropic’s guide warns against this: checking “a sequence of tool calls in the right order” is “too rigid and results in overly brittle tests, as agents regularly find valid approaches that eval designers didn’t anticipate.” Grade the final state instead, as agent benchmarks do. SWE-bench gives the model only the issue text and the codebase, then applies its patch and runs “the unit and system tests associated with the task instance”, tests taken from the real fix’s pull request (Jimenez et al., 2,294 tasks from real GitHub issues). τ-bench “compares the database state at the end of a conversation with the annotated goal state” (Yao et al.).

The outcome covers more than “the test passes”. The task above checks three things, and none of them reads the agent’s own claims:

  • The goal. A hidden test, copied in after the trial, passes. So does the rest of the suite.
  • Side effects. Only src/auth.rs changed, and no existing test was touched.
  • Termination. The agent stopped by itself, on a turn with no tool call (lesson 1’s termination condition), rather than being cut off at max_turns.
Never grade on evidence the agent can rig. A grader that checks whether the transcript contains {"passed": true} is grading the agent’s OBSERVE step, not the world. An agent that adds #[ignore] to the failing test, or deletes its assertion, gets passed: true and a green eval. That is the eval version of a symptom-patch, and only the hidden test and the unmodified-tests check catch it.

Three kinds of grader

  • Code: fast, cheap, objective, reproducible, but “brittle to valid variations”.
  • Model: flexible, scalable, “captures nuance”, but non-deterministic, costlier, and in need of calibration.
  • Human: “gold standard quality”, but expensive and slow.

That summary follows Anthropic’s guide, which recommends “deterministic graders where possible, LLM graders where necessary”. Prefer code whenever success is checkable state, but expect brittleness: in the same guide Claude Opus 4.5 first scored 42% on CORE-Bench partly because the grader rejected “96.12” when it expected “96.124991…”. With grading bugs fixed and a looser scaffold, the score “jumped to 95%”.

Some criteria aren’t state. Did the agent’s final message correctly say why the token check was wrong? For that you use LLM-as-judge: a second model that grades the transcript or outcome against an explicit rubric. Anthropic’s guide recommends grading “each dimension with an isolated LLM-as-judge” and giving the judge “a way out”, an Unknown verdict:

{
  "grader": "llm_judge",
  "judge_model": "a different model from the agent under test",
  "reads": ["final_message", "diff"],
  "dimension": "explains_root_cause",
  "question": "Does the final message state that the expiry comparison in src/auth.rs was wrong, consistent with the diff?",
  "verdicts": ["yes", "no", "unknown"]
}

The judge is an instrument with known defects. Zheng et al. examined “position, verbosity, and self-enhancement biases”. Position bias was strong (most judges favoured the first answer shown), and every judge tested sometimes preferred an answer padded with repetition, GPT-4 least often. Some judges also favoured their own model’s answers, though the authors could not confirm that as a bias. Strong judges still reached “over 80% agreement” with human preferences, the level humans reach with each other (Judging LLM-as-a-Judge, 2023). Claude’s docs recommend using “a different model to evaluate than the model used to generate the evaluated output” (Build evaluations).

A judge is not objective until you have checked it. Hand-label a small set of transcripts, run the judge on the same set, and measure agreement before trusting its scores: judges “should be closely calibrated with human experts” (Anthropic). When it compares two answers, judge both orders and count a win only if it holds in both, as Zheng et al. do.

pass@k or pass^k: one success, or every time?

pass@k is the probability that at least one of k trials succeeds. It comes from code generation, where a test runner can pick the winner: Codex solved 28.8% of HumanEval problems with one sample but 70.2% with 100 samples per problem (Chen et al., 2021). pass^k is the probability that all k trials succeed. τ-bench introduced it to measure reliability, and found gpt-4o succeeding on under 50% of tasks with pass^8 under 25% in the retail domain. With per-trial success p and independent trials:

pass@k = 1 − (1 − p)^k        # rises toward 1 as k grows
pass^k = p^k                  # falls toward 0 as k grows
p = 0.75, k = 3pass@3 98.4%pass^3 42.2%p and k from Anthropic’s example

The two metrics answer different product questions. Anthropic: “pass@k for tools where one success matters, pass^k for agents where consistency is essential.”

The formulas assume you know p. From data, both papers estimate per task: with c passes in n ≥ k trials, pass^k = C(c, k)/C(n, k) and pass@k = 1 − C(n−c, k)/C(n, k), then average over tasks. Plugging p̂ into 1 − (1 − p̂)k instead “results in a consistent underestimate” (Chen et al., appendix A). Averaging per task also exposes a diagnosis. Two suites can share a pass^1 of 0.75: if every task has p = 0.75, pass^8 ≈ 0.10; if three quarters of tasks always pass and the rest never do, pass^8 stays at 0.75. A falling pass^k means flakiness on tasks the agent can do; one that stays flat below 1 means specific tasks it consistently fails, a capability gap or a broken task.

For an agent acting unattended, pass^k is the honest number. Nobody picks the best of five nightly runs. If an agent runs five nights in a row, a per-night success rate of 0.9 means a clean week only 0.95 ≈ 59% of the time.

Error bars: is the change bigger than the noise?

With one trial per task, a pass rate p̂ over n tasks has standard error SE = √(p̂(1−p̂)/n), and a 95% confidence interval is about p̂ ± 1.96·SE (Anthropic, A statistical approach to model evaluations, 2024, summarising Miller). That is the variance of a sample mean, σ²/n, applied to a Bernoulli trial. The bar shrinks like 1/√n, so halving it takes four times the tasks.

Worked example. Your baseline passes 31/50 tasks, and a new prompt passes 34/50:

baseline   p̂ = 0.62   SE = √(0.62·0.38/50) = 0.069   95% CI ≈ 49%–75%
new        p̂ = 0.68   SE = √(0.68·0.32/50) = 0.066
difference 0.06       SE = √(0.069² + 0.066²) = 0.095   95% CI ≈ −13 to +25 points

The interval contains zero by a wide margin: this run can’t tell you whether the prompt helped. Miller adds two corrections. Pair: both arms ran the same 50 tasks, so compare per task. If the new prompt fixed 5 tasks and broke 2, the per-task differences give 6 ± 10 points, still inconclusive but much tighter, and those 7 flipped tasks are the transcripts to read. Cluster: 50 tasks × 5 trials is not 250 independent samples, because trials of one task share its difficulty; clustered standard errors on popular evals “can be over three times as large as naive standard errors.”

This is also how the fourth layer of the four-layer diagnosis gets tested. Hold prompt, tools and memory fixed, swap only the model, and run the same tasks:

BASE    = {prompt: P, tools: T, memory: M, model: "model-a"}
VARIANT = BASE | {model: "model-b"}           # exactly one layer differs

a = run_suite(SUITE, BASE)                    # same tasks, same fixtures,
b = run_suite(SUITE, VARIANT)                 # several trials per task
diff, se = paired_difference(a, b, cluster_by="task")
# CI excludes 0  -> the model layer matters on this suite: that is your evidence
# CI includes 0  -> not shown on this suite: add trials or tasks before ruling it out

The same experiment tells you whether a multi-agent design earns its token multiplier on your task. A public benchmark score can’t: it measures someone else’s tasks, harness and graders, and the CORE-Bench jump shows how far the last two move a number. Emerging-ai lesson 3’s checks on headline claims (which metric, which baseline) apply to your own eval claims too.

Two suites, two jobs

A capability eval asks what the agent can do. It “should start at a low pass rate, targeting tasks the agent struggles with and giving teams a hill to climb”. A regression eval asks whether it still does what it used to, and “should have a nearly 100% pass rate” (Anthropic). Near 100%, any failure is a specific event to investigate. Run it on every change, as Hamel Husain runs his “Level 1” evals “on every code change” (Your AI Product Needs Evals). Capability tasks that become reliable “graduate” into the regression suite.

You don’t need a big suite to start: “20-50 simple tasks drawn from real failures is a great start.” The run_tests loop is task one. Lesson 6’s planted-instruction cases (prompt injection) belong in the regression suite, graded on outcome: did a consequential call run? Keep reading transcripts, because graders have bugs too: “You won’t know if your graders are working well unless you read the transcripts and grades from many trials.” A 0% pass rate over many trials “is most often a signal of a broken task, not an incapable agent.”

Mining production traces for new tasks belongs to lesson 8 (agent traces, golden signals), as does what a suite run costs (cost per task).

Check your understanding

1. Your grader passes a trial when the transcript shows run_tests returning passed: true. One passing trial’s diff adds #[ignore] to the failing test. What is wrong?

2. An agent succeeds on a task with probability 0.8 per independent trial. What are pass@3 and pass^3?

3. On a 30-task suite, a tool change moves the pass count from 18/30 (60%) to 20/30 (67%). At p ≈ 0.6 and n = 30, the SE is about 9 points. What can you conclude?

4. Your regression suite was 50/50. After a change it scores 49/50. What should you do?

Practice before next lesson

Pick one real failure from your own sessions: a wrong edit, a loop that wouldn’t stop, a test “fixed” the wrong way. Write it as a task in the JSON shape above, with an input, a fixture, at least one outcome grader, one side-effect check and one termination check. Then decide which suite it belongs in. If you can, run it five times and report the result as c/5 with its SE. At n = 5 that SE is large, and seeing how large is part of the exercise.

Primary resource

Anthropic Engineering, Demystifying evals for AI agents (January 2026). Written for agents, it defines this lesson’s vocabulary and covers grader types, pass@k vs pass^k, capability vs regression suites and reading transcripts, with real stories of graders being wrong. For the statistics, follow it with Miller’s Adding Error Bars to Evals, including power analysis: how many tasks you need before running anything.

Ask your teacher anything. Bring a moment from this session where something “worked” on the first try, such as an edit, a test run or a command. Work out together, honestly and without over-claiming about how the harness works inside, what its task and outcome grader would be, which side effects the grader should check, and what pass^k you would want before letting it run unattended.
