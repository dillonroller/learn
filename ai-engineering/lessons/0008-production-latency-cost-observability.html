Production Concerns: Latency, Cost, and Observability for Agentic Systems

Lesson 1 made one fact non-negotiable: every model call is stateless, so each step resends the whole transcript. Lesson 3 named the obvious price of that, “latency and dollars per token”, in its context rot warning, and lesson 4 warned that a symptom-patching sentence is sent “on every single call, forever”. This lesson turns those warnings into numbers you can compute. Once an agent is live you need three things: a cost and latency model per task (measure), a trace of every step so the four-layer diagnosis works on runs you never watched (log), and caps that stop a run before it costs 50× the median (budget).

Cost per task: price the loop, not the call

The unit that matters is the cost per task: everything one task spends across every model call it triggers, including the main loop, subagents, compaction calls and retries. Failed runs are paid for too, so divide by the success rate to get cost per solved task.

Let the stable prefix (system prompt plus tool schemas) be P tokens, and let each step append g tokens (the tool call plus its result). Step k sends P + g(k−1) input tokens, so n steps send:

input tokens nP + g·n(n−1)/2growth O(n²)output tokens n·o

Worked example, illustrative numbers: the auth.rs agent with P = 20k, g = 2k, n = 30 and o = 300 output tokens per step. Input is 600k (prefix term) + 870k (growth term) = 1.47M tokens; the 30th call alone sends 78k. Price output at 5× input and the 9k output tokens cost 45k units, 3% of a 1.515M-unit bill. 92% pays for tokens the model already saw on an earlier step. Doubling n multiplies the bill by 3.19, not 2.

Transcript resend cost: cumulative input grows with the square of the step count. Statelessness means paying for the history again on every step. The growth term overtakes the prefix term once n − 1 exceeds 2P/g (20 here, so from n = 22 on): short loops are prefix-dominated, long loops history-dominated. Output costs more per token, but in a long loop resent input usually dominates. Find the largest term before optimizing anything.

Step counts are random, so budget the expected value. Write the cost as Σk ck·1[N ≥ k], where ck is step k’s cost; linearity of expectation gives E[cost] = Σk ck·Pr(N ≥ k), no independence needed. Since ck grows with k, the tail of N is weighted by the most expensive steps. If 499 tasks in 500 take 20 steps and one loops for 200, mean steps rise 1.8% but mean cost rises 10.7%: that one run costs 54× a typical task. Lesson 5’s multi-agent multiplier compounds this: each worker is its own loop with its own prefix and quadratic curve, so price each worker this way and add the lead.

Prompt caching: pay full price for the stable prefix once

The API caches by matching the start of each request against content it processed recently. Per the Claude docs (as of October 2026), the prefix runs tools → system → messages, and “changes at each level invalidate that level and all subsequent levels.” Prices are multipliers on base input: a cache read costs 0.1× (a few of the newest models charge less), a 5-minute write 1.25×, a 1-hour write 2×. The default lifetime is 5 minutes, refreshed free on each read. Responses report cache_read_input_tokens, cache_creation_input_tokens and input_tokens; total input is their sum.

With automatic caching, step k reads the previous request at 0.1× and writes only the new g tokens at 1.25×. The same task drops from 1.515M to 0.282M units, 5.4× cheaper. The resent share falls from 92% to 49% and output rises from 3% to 16%: once history is cached, writes and output matter again. Doubling n now costs ×2.57, since reads still grow with k.

  • Keep the prefix byte-stable: no timestamps or request ids in the system prompt, a deterministic tool order, dynamic content after the last breakpoint. The docs’ “common mistake”, a breakpoint on changing content, means “You pay for a fresh cache write on every request and never get a read.”
  • Compaction costs an extra call and a rebuild. The summarization call reads the warm cache, but the new, shorter history shares no prefix with the old one, so the messages level is written again (tools and system stay cached), as Claude Code’s caching docs state; they advise compacting at natural breaks. A model switch also starts a fresh cache.
  • Pauses outlive the cache. A human approval or slow worker longer than 5 minutes means the next call rewrites the prefix.
Caching fixes the price of a resent sentence, not its attention cost. A 200-token symptom-patch sentence costs 6,000 units over a 30-step task uncached, about 830 cached. The model still reads it every step, so the context rot remains.

Latency is a distribution, and fan-out lives in the tail

A task’s latency is a sequential sum: each step’s time to first token plus generation, each tool call, any approval wait. Every term is random, so watch percentiles, not the mean. Two agents can share a mean and differ wildly in variance: A takes 55–65 s every time; B takes 45 s on 95% of tasks and 345 s on the rest. Both average 60 s, but B’s p99 is 345 s. “Most metrics are better thought of as distributions rather than averages” (SRE ch. 4).

Parallel workers finish when the slowest does. If each of m independent workers is slow with probability p, the task is slow with probability 1 − (1−p)m. Dean and Barroso’s The Tail at Scale (CACM, 2013): with one slow response in 100 per server and a fan-out of 100, “63% of user requests will take more than one second.” With 8 workers the lead’s median wait is one worker’s p92, since 0.9178 = 0.5. That is the tax on orchestrator-worker fan-out. Levers:

  • Parallel tool calls for independent reads turn a sum into a max. Cap fan-out and time out stragglers, continuing with partial results.
  • Hedge: after the p95 expected latency, launch a duplicate and keep the first finisher. In the paper a hedge sent after 10 ms cut a 1,000-key BigTable read’s 99.9th percentile from 1,800 ms to 74 ms for 2% more requests. Hedge only idempotent reads: a hedged edit_file runs twice and widens the blast radius.
  • A smaller model for subtasks; streaming shows first tokens sooner but does not shorten the task.
  • Batch work nobody waits on: the Message Batches API costs 50% less, with “most batches finishing in less than 1 hour,” and stacks with caching.

The agent trace: the transcript, made queryable

OpenTelemetry’s vocabulary fits agents directly. A trace is “the path of a request through your application”. A span is “a unit of work or operation” with a name, a parent id, start and end times, attributes (key-value metadata) and events (timestamped logs). An agent trace has one root span per task and a child span for each model call, tool call, subagent and approval wait; a subagent’s own spans nest under its tool span.

with span("task", task_id=task.id) as root:                 # root span: one per task
    for step in range(BUDGET["max_steps"]):                   # lesson 1's loop, instrumented
        with span("model_call", step=step) as s:              # READ
            response = call_model(messages, tools=TOOLS)
            u = response.usage
            s.set(ttft_ms=response.ttft_ms, input_tokens=u.input_tokens,
                  cache_read=u.cache_read_input_tokens,
                  cache_write=u.cache_creation_input_tokens,
                  output_tokens=u.output_tokens,
                  stop_reason=response.stop_reason, cost=price(u))
        root.add(cost=s.cost)
        if root.cost > BUDGET["max_spend"]: return stop(root, "spend_cap")
        if response.tool_call is None:   return response.text
        with span("tool", name=response.tool_call.name) as t:    # ACT (subagents nest here)
            result = execute(response.tool_call.name, response.tool_call.arguments)
            t.set(is_error=result.is_error, result_tokens=count_tokens(result))
        append_observation(messages, response, result)            # OBSERVE
    return stop(root, "step_cap")

Monitoring must answer “what’s broken, and why?” (SRE ch. 6). Aggregates answer what: error rate and p99 cost per task went up. The trace answers why: every run_tests span returns 6 tokens with is_error false (the tool “worked”, so an error counter never fires), and the next step edits an unrelated function. That is lesson 4’s worked example, a tools-layer bug, found from a dashboard instead of a session you happened to watch. Anthropic’s Research write-up: “Adding full production tracing let us diagnose why agents failed and fix issues systematically.”

Count the whole tree, once. Per the Agent SDK cost docs, parallel tool calls in one turn yield messages sharing one id and identical usage, so deduplicate by id. The top-level usage field excludes subagent tokens; total_cost_usd and modelUsage include them, and their dollar figures are client-side estimates, not billing. Sum the wrong field and you undercount exactly the multi-agent runs that cost most.

Your own harness emits this shape. As of October 2026, Claude Code exports OpenTelemetry metrics (claude_code.token.usage, claude_code.cost.usage) and events (claude_code.api_request with duration, cost and cache tokens; claude_code.tool_result; claude_code.api_error). Its beta traces nest claude_code.llm_request and claude_code.tool spans under a claude_code.interaction root, time permission waits in a claude_code.tool.blocked_on_user span, and put subagent spans under the parent’s tool span. Prompts are redacted by default: log structure and numbers, keep content behind a flag.

Runtime budgets: the termination condition, grown up

Lesson 1’s termination condition was a max-iteration cap. A runtime budget caps steps, spend, fan-out (concurrency and depth), wall-clock time and per-tool time at once. Hitting a cap trips a circuit breaker: stop, return partial work and the reason, mark the root span, alert. As of 2026 the Agent SDK has maxTurns and maxBudgetUsd (which refuses new subagents and ends with error_max_budget_usd), and subagent depth defaults to 3, concurrency to 20.

BUDGET = dict(max_steps=40, max_spend=600_000,     # cost units, illustrative
              max_workers=4, worker_timeout_s=300, deadline_s=900)

def call_with_backoff(messages):
    for attempt in range(5):
        try:
            return call_model(messages, tools=TOOLS)
        except HttpError as e:
            if e.status != 429: raise
            if e.retry_after is None: raise          # spend-cap 429s carry no retry-after
            sleep(e.retry_after + jitter())          # honour it; never retry immediately
    raise GiveUp("rate limited")

Rate limits cap requests, input tokens and output tokens per minute with a continuously refilling token bucket; a rate-limit 429 carries a retry-after header (the 429 returned once your organization hits its tier’s monthly spend cap carries none, and retrying it fails until access resumes). On most models cache reads do not count toward the input-token limit, so caching raises throughput too. Long runs need durable execution: Anthropic’s Research team “can’t just restart from the beginning” and resumes “from where the agent was when the errors occurred.” A stateless model means the agent’s whole state is the transcript plus counters, so checkpoint them after each OBSERVE and make tools idempotent so a replayed step does not apply twice. Every trace that tripped a budget then becomes a regression eval task, and its fix is judged with error bars.

Golden signals for agents

“If you can only measure four metrics of your user-facing system, focus on these four” (SRE ch. 6). Adapted to agents:

  • Latency: task duration at p50 and p99 per task type, plus time to first token per call. Track failures separately, because “a slow error is even worse than a fast error!”
  • Traffic: tasks per minute, steps per task, tokens per minute.
  • Errors: failed tasks, tool errors per tool, API 429s and 5xx, max_tokens stop reasons, budget trips. Count implicit errors too: runs that “finish” but fail the grader.
  • Saturation: rate-limit headroom, context-window fill per step, running subagents against the cap, spend against budget.

Add cost per task at p50 and p99 as a fifth signal, and set objectives on percentiles. The SRE book’s example is “99% of Get RPC calls will complete in less than 100 ms.” An agent version (illustrative): 95% of fix-test tasks finish within 5 minutes and under 400k units.

1. An uncached agent loop has a 10k-token prefix and adds 1k tokens per step. About how many input tokens does a 20-step task send in total?

2. A lead agent fans out to 10 parallel workers and waits for all of them. Each worker independently has a 5% chance of taking over 4 minutes. How often does the whole task take over 4 minutes?
