Digital Signatures: Authentication From the Same Number Theory

Lesson 4 ended on a gap: nothing tells Alice that the B = 19 she received came from Bob, so a man-in-the-middle can run Diffie-Hellman separately with each of them. Lesson 2's RSA key hid a message from everyone but its owner; run the same key the other way and it does the opposite job — everyone can read the message, but only the owner could have produced the number attached to it. You'll sign and verify with that (3233, 17, 2753) key, forge textbook RSA signatures without it, build DSA on the Diffie-Hellman group mod 23, recover a DSA private key from two signatures that reused a random number, and then close that gap.

What a signature is — and what it isn't

A digital signature scheme is three algorithms:

  • KeyGen() → (sk, pk): a private signing key and a public verification key.
  • Sign(sk, m) → σ: only the holder of sk can run it.
  • Verify(pk, m, σ) → accept or reject: anyone can run it.

Correctness means Verify always accepts an honest signature. Security means that without sk no efficient attacker can produce a pair (m, σ) that Verify accepts and the signer never signed — even after collecting signatures on messages of their own choosing (formally, existential unforgeability under chosen-message attack). The key roles flip relative to encryption: in RSA encryption the public key produces and the private key consumes; in signing, the private key produces and the public key checks.

What you get, as NIST's Digital Signature Standard (FIPS 186-5) puts it: integrity (alter m and verification fails), authentication of the signer, and non-repudiation — because only the private key could have produced σ, a third party such as a judge can verify it too, and the signer cannot credibly deny it later. Rivest, Shamir and Adleman made the same point in the 1978 RSA paper: a signature must be message-dependent and signer-dependent. What you do not get is secrecy: m travels in the clear next to σ. Signatures prove; they don't hide.

RSA signatures: the same key, run backwards

With Bob's RSA key — public (n = 3233, e = 17), private d = 2753 — textbook RSA signing is:

Sign:    σ = m^d mod n
Verify:  accept iff σ^e mod n = m
Worked example: Bob signs m = 65 σ = 652753 mod 3233 = 588 (12 bits of 2753 through square-and-multiply). Anyone holding the public key checks it with 17 = 100012: 
bit 1: r = 1² · 588 mod 3233         = 588
bit 0: r = 588² mod 3233             = 3046
bit 0: r = 3046² mod 3233            = 2639
bit 0: r = 2639² mod 3233            = 439
bit 1: r = 439² mod 3233 · 588
         = 1974 · 588 mod 3233       = 65  ✓
The result equals m, so Verify accepts (65, 588). Compare RSA encryption: encrypting 65 gave 2790. Same key, same message, different number, opposite job — 2790 hides 65 from everyone but Bob; 588 sits next to a public 65 and proves Bob approved it.

Why it works is the lesson 2 correctness proof with the exponents in the other order: σe = md·e, and d·e = 17 · 2753 = 46801 = 1 + 15 · 3120, so σe = m · (m3120)15 ≡ m (mod 3233) by Euler's theorem (for m coprime to n, as 65 is; the linked proof covers the rest). Forging a signature on a given m from the public key alone means computing an e-th root of m mod n — exactly the RSA problem.

Signing is not "encrypting with the private key" That slogan is a coincidence of textbook RSA, where the map x ↦ xd that signs happens to be the same map that decrypts. DSA below has no encryption counterpart at all, and even real RSA uses different, incompatible encodings for the two jobs — RSASSA-PSS for signatures, RSAES-OAEP for encryption (RFC 8017). Treat Sign and Verify as algorithms in their own right.

Forging textbook RSA without the key

Textbook RSA signatures fail the security definition in two ways, neither of which needs d. The first is an existential forgery: any valid (m, σ) the signer never signed, even if m is a meaningless number. Choose σ first, then let the public key tell you which m it signs. With σ = 2: 217 = 131072 = 40 · 3233 + 1752, so (1752, 2) verifies under Bob's key. Bob never saw 1752.

The second is malleability: (ad)(bd) = (ab)d, so signatures multiply. Get Bob to sign the harmless-looking 2 and 3 — σ(2) = 1027, σ(3) = 1857 — and then 1027 · 1857 = 1907139 = 589 · 3233 + 2902, and 290217 mod 3233 = 6. That's a valid signature on 6, made with no key. Pushed further, the same algebra signs any m the attacker wants: get Bob to sign the random-looking m · re mod n, then divide the answer, md · r, by r (Boneh & Shoup §13.3.1). So the e-th-root barrier above protects only against an attacker who never sees a signature.

The fix: hash-then-sign Sign a hash instead: σ = H(m)d mod n; accept iff σe ≡ H(m). Here H is a black box — a public cryptographic hash function, easy to compute, infeasible to invert, outputs unrelated to each other. The attacks die: σ = 2 now yields 1752 = H(m), and the forger needs an m that hashes to 1752 (inverting H); multiplying two signatures now signs the number H(m1) · H(m2) mod n, useless unless she can find a message hashing to it — inverting H again. With H's outputs covering a large fraction of 0…n−1 this is the full domain hash scheme, proven secure assuming the RSA problem is hard and H is modeled as a truly random function, the “random-oracle model” (Boneh & Shoup §13.3–13.4); deployed RSA uses the related PSS and PKCS #1 v1.5 encodings. New obligation: if H(m) = H(m′), a signature on m also signs m′, so H must be collision resistant.

DSA: a signature built on the discrete log

The Digital Signature Algorithm, which NIST chose in 1991 (Boneh & Shoup §19.3), rests on the discrete log problem instead of RSA's. It works in a subgroup of prime order q inside the nonzero residues mod p, with q dividing p − 1 (§4 of FIPS 186-4, now withdrawn but still DSA's full specification):

Setup:  primes p, q with q | p−1;  g of order q
KeyGen: private x in [1, q−1];  y = g^x mod p
Sign h = H(m) with a fresh secret nonce k:
        r = (g^k mod p) mod q
        s = k⁻¹ · (h + x·r) mod q,   σ = (r, s)
Verify: w = s⁻¹,  u1 = h·w,  u2 = r·w   (mod q)
        accept iff (g^u1 · y^u2 mod p) mod q = r

The toy group: p = 23, and q = 11 divides 22. The Diffie-Hellman primitive root 5 has order 22; its square g = 52 mod 23 = 2 has order 11 — its powers run 2, 4, 8, 16, 9, 18, 13, 3, 6, 12, 1 and repeat. The signer picks x = 7, so y = 27 = 128 = 5 · 23 + 13, giving y = 13.

Worked example: sign h = 5 with k = 3, then verify Every inverse is a modular inverse mod q = 11. 
Sign
  g^k = 2^3 mod 23            = 8
  r   = 8 mod 11              = 8
  k⁻¹ = 3⁻¹ mod 11            = 4    (3·4 = 12 ≡ 1)
  h + x·r = 5 + 7·8           = 61
  s   = 4·61 = 244 mod 11     = 2    σ = (8, 2)

Verify with y = 13
  w   = 2⁻¹ mod 11            = 6    (2·6 = 12 ≡ 1)
  u1  = 5·6 = 30 mod 11       = 8
  u2  = 8·6 = 48 mod 11       = 4
  2^8 = 256 mod 23            = 3
  13^4: 13² = 169 ≡ 8, 8²     ≡ 18
  3·18 = 54 mod 23            = 8
  v   = 8 mod 11              = 8 = r  ✓

Why the verifier lands on r: gu1 · yu2 = gh·w · gx·r·w = gw(h + x·r), and w = s−1 = k · (h + x·r)−1, so the exponent collapses to k (exponents live mod q because g has order q). The verifier rebuilds gk without ever learning k or x. Recovering x from y is the discrete log problem — trivial at p = 23, but real DSA used p of 1024 to 3072 bits with q of 160 to 256 bits (FIPS 186-4 §4.2).

DSA itself is now legacy. As of 2026 the current Digital Signature Standard is still FIPS 186-5 (2023), and it states that DSA "is no longer specified in this standard and may only be used to verify previously generated digital signatures"; its approved schemes are RSA, ECDSA and EdDSA, while the post-quantum ML-DSA and SLH-DSA have standards of their own. ECDSA is this same algorithm with the mod-p group swapped for an elliptic-curve group (r comes from the x-coordinate of the point kG) — lesson 6 builds that group and runs ECDH on it.

Reuse the nonce once, lose the key

The k in DSA is a nonce — a number used once — and FIPS 186-4 (§4.5) demands a new secret one for every signature. Suppose the signer above signs a second hash, h2 = 9, with the same k = 3. Then r is again 8 (r depends only on k), and s2 = 4 · (9 + 56) = 260 ≡ 7 (mod 11). An eavesdropper now holds (8, 2) on h1 = 5 and (8, 7) on h2 = 9, and the matching r is her signal that k repeated. (At real sizes two different k essentially never share an r. In this toy group they can, since k = 1 and k = 7 both give r = 2, so she checks gk at the end.) Subtracting the two signing equations cancels the x·r term: s1 − s2 ≡ k−1(h1 − h2). So:

Worked attack: two inverses to the private key 
k = (h1 − h2) · (s1 − s2)⁻¹ mod 11
  = (−4) · (−5)⁻¹ = 4 · 5⁻¹
  = 4 · 9 = 36 mod 11 = 3        (5·9 = 45 ≡ 1)
check: (2^3 mod 23) mod 11 = 8 = r  ✓
x = (s1·k − h1) · r⁻¹ mod 11
  = (2·3 − 5) · 8⁻¹ = 1 · 7 = 7  (8·7 = 56 ≡ 1)
check: 2^7 mod 23 = 13 = y  ✓
No discrete log was solved. One repeated nonce turned two public signatures into the private key.

This is not hypothetical. Sony's PlayStation 3 used ECDSA with the same k for every signature, and its signing key was recovered this way (Corbellini; Boneh & Shoup §19.3). Exact repeats aren't the only danger: k must be uniformly random, and RFC 6979 warns that "even slight biases in that process may be turned into attacks." Its fix derives k deterministically from the private key and the message hash: the same message always gets the same k (and the same, harmless, signature), different messages get unrelated ones. FIPS 186-5 approves this "deterministic ECDSA".

Closing the gap: signed Diffie-Hellman

The Diffie-Hellman man-in-the-middle worked because A and B were unauthenticated numbers: Eve replaced each with her own and held one shared secret with Alice and another with Bob. The fix is to have each party sign its Diffie-Hellman value — and the rest of the exchange so far — with a long-term signing key whose public half the other side already trusts. With the course's Diffie-Hellman numbers (p = 23, g = 5, a = 6, b = 15), and H(8 ‖ 19) meaning the hash of the two values concatenated:

Alice → Bob:  A = 8
Bob → Alice:  B = 19,
              σ_B = Sign(sk_B, H(8 ‖ 19))
Alice:        Verify(pk_B, H(8 ‖ 19), σ_B) ✓
              key = 19^6 mod 23 = 2
Bob:          key = 8^15 mod 23 = 2

If Eve swaps 19 for her own value E, Alice checks σB against H(8 ‖ E) and it fails; to get through, Eve must produce Sign(skB, H(8 ‖ E)) herself — a forgery. Including Alice's fresh A also means a signature Bob made in yesterday's handshake won't verify today. Alice signs her side the same way when Bob needs to know who she is. TLS 1.3 does exactly this: in its CertificateVerify message the server signs a hash of the handshake transcript — which contains both key shares — as "explicit proof that an endpoint possesses the private key corresponding to its certificate" (RFC 8446 §4.4.3).

What a valid signature still doesn't prove σB proves that whoever sent it holds skB — not that skB belongs to the Bob Alice meant. If Eve can get Alice to accept Eve's public key as "Bob's", she signs her own values and the attack is back. Binding keys to names is the job of certificates, which this course leaves out. And nothing here encrypts: the signature authenticates the exchange; the shared secret does the hiding.

Signatures and quantum computers

Each scheme inherits its hardness assumption's fate. RSA signatures fall once n can be factored by Shor's algorithm; DSA and ECDSA fall to Shor's discrete-log variant, which rests on the same quantum period-finding as order-finding. Lesson 7 sorts out what survives and names NIST's post-quantum standards, and lesson 8 shows how to build a signature from nothing but a hash function.
