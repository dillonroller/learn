Hash Functions & Merkle Trees: The Other Half of Practical Cryptography

Lesson 5 signed H(m) and treated H as a black box. Lesson 4’s Diffie-Hellman ended on a group element, not a key. Lesson 7’s standards included a signature with no number theory in it at all. All three run on one primitive. This lesson opens the box only as far as public-key cryptography needs: what a hash promises, what the birthday bound says breaking it costs (classically and with Grover), and the Merkle tree, which commits to a whole list with one digest. The win: verify a Merkle inclusion proof hash by hash — then watch the same move turn one-time hash signatures into SLH-DSA.

What a cryptographic hash function promises

A cryptographic hash function H maps an input of any length to a fixed n-bit digest. It is public, keyless and deterministic: anyone can compute H(x), and the same x always gives the same digest. The workhorse is SHA-256 (n = 256, messages under 264 bits; FIPS 180-4), a Merkle–Damgård design; SHA-3 (FIPS 202) is a Keccak “sponge” (Boneh & Shoup §8.4, §8.8). Neither contains number theory, and this course keeps their insides closed. Flip one input bit (“c” is 0x63, “C” is 0x43) and 134 of the 256 output bits change:

SHA-256("abc") = ba7816bf8f01cfea…f20015ad
SHA-256("abC") = 0a2432a1e349d8fd…6f3b8f76

Security is three games, each won by finding inputs:

  • Preimage resistance (one-wayness): given y = H(x) for an unknown, unpredictable x, find any x′ with H(x′) = y.
  • Second-preimage resistance: given a specific x, find a different x′ with H(x′) = H(x). Someone else fixed the target.
  • Collision resistance: find any x ≠ x′ with H(x) = H(x′). The attacker chooses both.

Collisions must exist (far more possible inputs than 2256 digests), so “resistant” means infeasible to find, not impossible. The three differ. A second-preimage finder is a collision finder (pick any x, find its x′), so collision resistance implies second-preimage resistance but not the reverse; how either relates to preimage resistance depends on how much H compresses (Rogaway & Shrimpton, 2004). Collision resistance is the strongest, and the first to fall, as SHA-1 shows below. Contrast the hash in a hash table, which only spreads keys over buckets and assumes no adversary. And a hash is not encryption: no key, no way back.

The birthday bound: n bits buy n/2 against collisions

Hash k random inputs into N = 2n digests. Each of the C(k, 2) = k(k−1)/2 pairs collides with probability 1/N, so by linearity of expectation (no independence needed) the expected number of colliding pairs is C(k, 2)/N. It reaches 1 at k ≈ √(2N) = √2 · 2n/2: pairs grow like k², so collisions arrive after about the square root of the digest space. That is the generic birthday attack, and it works against every hash (Boneh & Shoup §8.3).

Worked example: 16-bit digests (the first 4 hex digits of SHA-256) N = 65,536, so C(k, 2) = N at k ≈ 362. Summing the exact probabilities, the first repeat comes on average at try 321.5, and 302 tries already give 50.07% odds. Hashing vote-0, vote-1, vote-2, … collides at try 326: 
SHA-256("vote-106") = 8d82f8f11dcb4417…
SHA-256("vote-325") = 8d82f30d9161b3e1…
Hitting one given 16-bit digest (a preimage) takes about 65,536 tries, some 200 times more.

So an ideal n-bit hash costs about 2n evaluations to invert and 2n/2 to collide: 280 collisions for 160-bit SHA-1, 2128 for SHA-256. Finding a preimage is exactly unstructured search, so Grover needs about 2n/2 evaluations, and for a black-box hash no quantum algorithm does better. Brassard, Høyer & Tapp find collisions in about 2n/3 queries, but on a quantum computer of size about 2n/3; Bernstein (2009) shows a classical machine of size 2n/6 already reaches that time at better price-performance.

Ideal n-bit hashClassicalQuantum
Preimage2n (SHA-256: 2256)2n/2, Grover (2128)
Second preimage2n (2256)2n/2, Grover (2128)
Collision2n/2 (2128)2n/3 queries, no cheaper in real cost

Hence NIST’s IR 8105: SHA-2 and SHA-3 need “larger output”, while RSA, ECDSA and ECDH are “no longer secure” — the Grover-only column of lesson 7’s classification. None of this is proven: like factoring, hash security is a belief calibrated by the best attacks anyone has found.

Where public-key cryptography leans on H

  • Hash-then-sign needs collision resistance. If H(m) = H(m′), a signature on one verifies for both. When Mallory drafts what you sign, she chooses both inputs — Google’s SHA-1 collision announcement pictured two insurance contracts with drastically different terms. Second-preimage resistance doesn’t help: she never matches a digest she didn’t choose. The 2017 SHA-1 collision took about 263.1 compression-function calls instead of the generic 280 (216.9 ≈ 122,000 times less), while SHA-1 still signed documents and TLS certificates.
  • DSA signs h = H(m) (lesson 5), with the same requirement.
  • Diffie-Hellman’s output gets hashed. The shared secret gab is a structured group element, not a uniform key; TLS 1.3 feeds it into HKDF-Extract, a hash-based key derivation (RFC 8446 §7.1).

Merkle trees: one digest for a whole list

A Merkle tree hashes each leaf, then hashes adjacent pairs, parent = H(left ‖ right), level by level up to one root. Publishing the root commits you to the whole list: changing any leaf changes every hash on its path, so a different list with the same root needs an H collision somewhere on that path (Boneh & Shoup §8.9) — provided a leaf can never be mistaken for an internal node. Without that, the 64-byte concatenation of two child hashes is itself a valid leaf, and a shorter list reaches the same root with no collision at all. Certificate Transparency’s RFC 6962 rules this out by prefixing leaves with a 0x00 byte and internal nodes with 0x01, a domain separation it calls “required to give second preimage resistance”. The explorer builds that tree with real SHA-256 over eight public values from the RSA and Diffie-Hellman lessons, showing 8 of each hash’s 64 hex digits. Computing hashes…

  


  
An inclusion proof (RFC 6962’s audit path) for leaf i is one sibling hash per level: log2 n hashes. The verifier hashes the leaf, folds in each sibling in turn and compares the result with the published root. The leaf index in binary, lowest bit first, says which side each sibling goes on: bit 1 means you are a right child, so the sibling goes left.

  

    Worked proof: L5 = “e=17”, index 5 = 101₂
    
leaf    H(00‖e=17)              = d9982454
bit 1   sibling on the left
        H(01‖88804593‖d9982454) = cbf5e1fa
bit 0   sibling on the right
        H(01‖cbf5e1fa‖7a48accf) = 5a440040
bit 1   sibling on the left
        H(01‖cdc181a0‖5a440040) = a2308150
root    a2308150 = published root  ✓

    Three hashes, not seven other leaves. 4 leaves need 2, 8 need 3, 220 = 1,048,576 need 20 (640 bytes).
  

  
Step through L5 in the explorer and check each line. Then change L5 to e=3: exactly four hashes change, and the proof fails against the published root. Tick “tamper” and one bad sibling breaks everything above it. In the wild, CT logs serve audit paths proving a certificate was logged; Git names every object by its SHA-1 hash, and tree objects list their children’s hashes (Pro Git §10.2), with SHA-256 the planned default for new repositories in Git 3.0 (unreleased as of October 2026); Bitcoin block headers carry only the transactions’ Merkle root, and light clients verify payments with a Merkle branch (Nakamoto §7–8).

  

    What a Merkle root doesn’t give you
    It binds; it does not hide. Guessable leaves can be brute-forced: a root over eight yes/no votes is one of only 28 = 256 possible roots. And a valid proof shows the leaf is in the list the root commits to, not that the root is the right one — CT logs sign their roots, which is a signature’s job, not the tree’s.
  


  
Signatures from nothing but a hash

  
Around 1975, in a Berkeley coffee house, Whitfield Diffie posed the signature problem to Leslie Lamport, who solved it on the spot (Lamport, 1979). A Lamport one-time signature on b-bit digests:

  
KeyGen: secret x[i][0], x[i][1], i = 1…b (random)
        public y[i][j] = H(x[i][j])
Sign d: reveal x[i][d_i] for each digest bit d_i
Verify: H(revealed_i) = y[i][d_i] for every i

  
Forging on a new digest means inverting H on an unrevealed y, so one-time security rests on preimage resistance (Boneh & Shoup §14.1). With SHA-256 and b = 256: a 16,384-byte public key and an 8,192-byte signature. Sign twice with one key, though:

  

    Worked example: one key, two 4-bit digests
    
sign 1011: reveal x1,1  x2,0  x3,1  x4,1
sign 0110: reveal x1,0  x2,1  x3,1  x4,0
both secrets public at positions 1, 2, 4
signable: every digest with bit 3 = 1
  0010 0011 0110 0111 1010 1011 1110 1111

    Eight digests, six never signed: an existential forgery. At full size the leak is fast: after k signatures a position stays pinned with probability 21−k, so after five only about 16 of 256 are pinned, and a forger needs about 216 hashes to find a message that fits.
  

  
Merkle’s fix: make 2h one-time key pairs, put the hashes of their public keys at the leaves of a Merkle tree, and publish only the 32-byte root. Signature number i is the one-time signature with key i, plus that public key, plus its audit path; the verifier checks the one-time signature, hashes the key into a leaf and recomputes the root — the skill you just practised (Boneh & Shoup §14.6). No leaf may be used twice, so the signer must track which are spent, as NIST’s stateful LMS and XMSS do (SP 800-208).

  
SLH-DSA (FIPS 205, August 2024), standardized from SPHINCS+, drops the state: a tree of Merkle trees so large that the one-time (strictly, few-time) key at the bottom is chosen by a randomized hash of the message, so a key landing on enough messages to break is negligibly unlikely and no record of spent keys is needed. Its security “relies on the presumed difficulty of finding preimages for hash functions as well as several related properties” — no factoring, discrete logs or lattices. The price: a 32-byte public key but a 7,856-byte signature for the smallest parameter set (FIPS 205, Table 2). NIST calls it “a backup method in case ML-DSA proves vulnerable”: if lattices fall, hashes still stand.


  
Eight lessons, five assumptions

  
Everything in this course stands on something believed, not proven: RSA on the RSA problem and behind it factoring; Diffie-Hellman and DSA on the discrete log problem; ECDH and ECDSA on the ECDLP; ML-KEM and ML-DSA on the module form of LWE (ML-DSA also on a variant of its sibling, Module-SIS: FIPS 204 §3.2); and all of them, through hash-then-sign, key derivation and SLH-DSA, on the hash properties above. Shor’s period-finding breaks the first three; Grover only halves the preimage exponent of the last; LWE is believed to resist both. That is the precise version of “quantum computers break encryption” this course set out to earn.
