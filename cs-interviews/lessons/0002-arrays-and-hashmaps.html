Arrays & Hash Maps

Hand a candidate a “find a pair”, “find a duplicate” or “group these” problem and the interviewer is really asking: do you see that the inner loop is a lookup in disguise? Lesson 1 left has_duplicate with a promise: “Can you do better? (Yes: use a HashSet → O(n) time, O(n) space).” This lesson keeps it. Rust’s docs open their collections guide with “you should probably just use Vec or HashMap”. Today’s win: turn an O(n²) pair, duplicate or grouping search into one O(n) pass, and say what it costs in memory.

Vec: the cost model

A Vec<T> is a dynamic array: one contiguous buffer plus a length and a capacity. Contiguity buys O(1) indexing and makes every gap in the middle expensive (std cost table, Vec docs):

OperationCostWhy
v[i]O(1)address arithmetic
push(x)O(1) amortizedrare reallocation
pop()O(1)nothing shifts
insert(i, x), remove(i)O(n − i)the tail shifts (insert also amortizes growth)
swap_remove(i)O(1)last element fills the hole; order lost
contains(&x)O(n)linear scan: what hashing removes

Amortized cost is the total cost of a long run of operations divided by its length. A push that finds the buffer full copies everything into a bigger one, so that call is O(n), but growth is geometric, so such calls are rare. Pushing 1,000,000 i32s into Vec::new() on Rust 1.97 (2026) took capacity through 4, 8, 16, …, 1,048,576: 19 allocations (the first, from empty, copies nothing) moving at most 4 + 8 + … + 524,288 = 1,048,572 elements, about 1.05 per push. The docs promise no growth factor, only that “whatever strategy is used will of course guarantee O(1) amortized push”. Know n up front? Vec::with_capacity(n) skips the copies.

Common interview trap Draining a Vec with v.remove(0) in a loop looks linear but shifts every remaining element each time: n(n−1)/2 moves, 499,999,500,000 for a million elements. Amortization won’t rescue you: the std table prices remove(i) at O(n − i) per call, with no *, so every call pays its own shift. Iterate, use swap_remove if order is irrelevant, or use a real queue (lesson 4).

Hash maps: how expected O(1) is earned

A hash table is an array of m slots plus a hash function mapping each key to a slot. Two keys in one slot is a collision, resolved by chaining (a short list per slot) or open addressing (probing other slots) (Sedgewick & Wayne §3.4). The table resizes to keep the load factor α = n/m below a constant; each O(n) rehash is amortized like Vec growth. Bounded α means a constant expected number of probes. With chaining and a hash drawn from a universal family, a key’s chain has expected length at most 1 + (n−1)/m (MIT 6.006, L4). With linear probing at α = ½, a hit averages about ½(1 + 1/(1 − α)) = 1.5 probes under a uniform-hashing assumption (Sedgewick & Wayne, Prop. M). “Expected” is literally an expectation over the hash’s randomness. If every key collides, each operation is O(n).

The std table writes get as O(1)~ and insert as O(1)~*: ~ marks expected, * amortized. From the HashMap docs:

  • It is “implemented with quadratic probing and SIMD lookup”: open addressing.
  • The default hasher is currently SipHash 1-3, randomly seeded and “selected to provide resistance against HashDoS attacks”, where an attacker picks keys that all collide. Faster hashers win on small keys like integers but typically drop that protection: a trade-off, not a free speed-up. Cryptographic hash functions are a different tool again (Hash Functions & Merkle Trees).
  • Keys need Eq + Hash with k1 == k2 → hash(k1) == hash(k2); #[derive(PartialEq, Eq, Hash)] gives you that. f64 is neither, so it can’t be a key.
  • Iteration order is “arbitrary”, and with a per-map random seed it can differ between runs of the same program. Need order? Sort the output or use BTreeMap (O(log n), sorted keys; trees are lesson 5).
Why interviewers care Interviews mostly care about the hash table’s average case (Tech Interview Handbook), but “what’s the worst case?” is a standard follow-up. “Expected O(1), O(n) if keys collide, which Rust’s seeded hasher guards against” takes five seconds and shows you know what the O(1) hides.

Four patterns that turn O(n²) into O(n)

Look at the brute force’s inner loop. If it searches for something you could have remembered, remember it in a hash table.

1. The seen-set

Cue: “have I seen this before?” Use a set when you “just want to remember which keys you’ve seen”; in lesson 6 it becomes the visited set. Lesson 1’s function, same signature:

use std::collections::HashSet;

fn has_duplicate(v: &[i32]) -> bool {
    let mut seen = HashSet::with_capacity(v.len());
    for &x in v {
        if !seen.insert(x) { return true; }  // false: x was already there
    }
    false
}
// O(n) expected time, O(n) space. "Can you do better?" Time, no: every element
// must be read. Space, yes, if you may mutate: sort_unstable, compare neighbours.
TimeO(n) expectedSpaceO(n)

2. Complement lookup (Two Sum)

Cue: “find two elements with property P” where one element pins down its partner; for a sum, x needs target − x. Map value → index and the pair search becomes a lookup. The order inside the loop is the trick: look up first, insert second.

use std::collections::HashMap;

fn two_sum(nums: &[i32], target: i32) -> Option<(usize, usize)> {
    let mut index_of: HashMap<i32, usize> = HashMap::new();
    for (i, &x) in nums.iter().enumerate() {
        if let Some(&j) = index_of.get(&(target - x)) {  // 1. look up
            return Some((j, i));
        }
        index_of.insert(x, i);                           // 2. then remember
    }
    None
}
// O(n) expected time, O(n) space. Next question: "What if nums is sorted?"
// Two pointers: O(n) time, O(1) space.
TimeO(n) expectedSpaceO(n)

The sorted case is two pointers, and the complement idea returns as prefix-sum complements, both in lesson 3. Say aloud that target - x can overflow i32 at the extremes (debug builds panic); widen to i64 if the constraints allow it.

Trace it. At each index, choose the loop body’s next step. Wrong clicks explain themselves and change nothing.

TimeO(n) expectedSpaceO(n)
Common interview trap “Load the whole map, then look up complements.” With target 6 and a single 3, the 3 finds itself and you return (0, 0). Check-before-insert means the map holds only earlier elements, and [3, 3] still works because the second 3 finds the first.

3. Frequency counting

Cue: anagrams, “can A be built from B”, “appears exactly once”, majority. Only how many matters. The idiom is the entry API, whose or_insert returns &mut V (Rust Book §8.3):

let mut freq: HashMap<char, usize> = HashMap::new();
for c in s.chars() { *freq.entry(c).or_insert(0) += 1; }  // O(n) expected; O(d) space, d distinct chars

let mut cnt = [0u32; 26];                                 // a–z only: perfect hash
for b in s.bytes() { cnt[(b - b'a') as usize] += 1; }    // O(n), O(1) space

The array is a collision-free hash for a fixed alphabet, and 26 counters don’t grow with n, so it is O(1) space. Calling it O(n) is a common mistake. Ask about the character set first: a–z, bytes ([u32; 256]) or full Unicode (the map).

4. Canonical keys (grouping)

Cue: “group items that are equal up to some transformation”. Map each item to one representative of its class and use it as the key of a HashMap<Key, Vec<Item>>. For anagrams, sorted bytes or letter counts both work, since arrays and Vecs of hashable values are Eq + Hash.

fn group_anagrams<'a>(words: &[&'a str]) -> Vec<Vec<&'a str>> {
    let mut groups: HashMap<[u32; 26], Vec<&'a str>> = HashMap::new();
    for &w in words {
        let mut key = [0u32; 26];                    // letter counts, a–z only
        for b in w.bytes() { key[(b - b'a') as usize] += 1; }
        groups.entry(key).or_default().push(w);
    }
    groups.into_values().collect()                   // arbitrary order
}
// n words of length ≤ k: O(n·k) expected time. O(n) extra space: each key is
// 26 counters and the groups hold borrowed &str, not copies of the words.
// A sorted-bytes key (Vec<u8>) also works: O(n·k log k) time, O(n·k) space.
TimeO(n·k) expectedSpaceO(n)

Say the trade-off out loud

All four patterns make one move, a space-for-time trade-off: O(n) memory turns each “search the rest” into an expected-O(1) lookup. Hashing is “the most common example of a space-time tradeoff”. Know the other side of the deal:

ProblemHash versionLow-memory version
Any duplicate?O(n) time, O(n) spacesort in place + scan: O(n log n), O(1) extra, mutates input
Two SumO(n) time, O(n) spacesort (value, index) pairs + two pointers: O(n log n), and still O(n) for the pairs

The second row is the subtle one: sorting loses the indices, so you carry them and the saving evaporates. sort_unstable is “in-place (i.e., does not allocate), and O(n * log(n)) worst-case”; more in lesson 10. “O(1) extra” is the usual interview shorthand: strictly, its quicksort recursion is capped at 2·log₂ n deep, so O(log n) stack. Say so if pressed. Lesson 1’s talk-track, extended:

“Brute force is O(n²) time, O(1) space. Trading memory for time, one pass with a HashSet is O(n) expected time, O(n) space. If memory is tight and I may mutate the input, I’d sort in place and compare neighbours: O(n log n) time, O(1) extra.”

What would a Google interviewer ask next? “Worst case of your map?” (O(n) per operation under collisions). “What if values are in 0..n?” (a Vec<bool> indexed by value: a perfect hash, so worst-case O(1) per check instead of expected; still O(n) space). The remember-instead-of-recompute move returns as memoization in lesson 9.
