Two Pointers & Sliding Window

When a problem says sorted, subarray or substring, the interviewer is waiting for one move: replace the O(n²) double loop over every (i, j) with two indices that each move in one direction only. In lesson 2 you bought expected O(n) time with an O(n) hash map. These patterns often get the same O(n) time for O(1) extra space, which is the cheap side of the space-for-time trade-off. Today’s win: name the right tool within a minute, then write its loop with the right shrink condition.

Converging pointers

Put lo at the start of a sorted slice and hi at the end, and move them towards each other. Take sorted Two Sum (LeetCode’s “Two Sum II”). The interviewer expects a chain of answers: brute force over all pairs is O(n²); a binary search for each complement is O(n log n); converging pointers are O(n).

use std::cmp::Ordering;

fn two_sum_sorted(v: &[i32], target: i32) -> Option<(usize, usize)> {
    let (mut lo, mut hi) = (0, v.len().checked_sub(1)?);
    while lo < hi {
        let sum = v[lo] as i64 + v[hi] as i64; // i32 + i32 can overflow: widen
        match sum.cmp(&(target as i64)) {
            Ordering::Equal   => return Some((lo, hi)),
            Ordering::Less    => lo += 1, // v[hi] is the biggest partner left: v[lo] is dead
            Ordering::Greater => hi -= 1, // v[lo] is the smallest partner left: v[hi] is dead
        }
    }
    None
}
// O(n) time, O(1) space. The HashMap version: O(n) expected time, O(n) space.
TimeO(n)SpaceO(1)

Why moving lo is safe. If v[lo] + v[hi] is too small, then v[hi] is the largest value still in play, so v[lo] is too small with every remaining partner, and no answer uses it. The Greater case is the mirror image. Each step eliminates one index for good, so there are at most n − 1 steps. Laaksonen solves the same “2SUM problem” with a close variant in CPH §8.1. Say this argument out loud before the interviewer asks for it.

The same “discard the loser” argument powers Container With Most Water: the shorter line caps the area, and any pair keeping it with a closer partner is narrower and no taller, so drop the shorter side. Valid Palindrome converges on mirror positions. A cousin keeps one pointer per array: to merge sorted arrays of lengths n and m, advance whichever holds the smaller head, O(n + m) (TIH, Array), the heart of merge sort.

Common interview trap Converging pointers need a reason to discard a side, such as sorted order, a dominance argument or mirror symmetry. Unsorted Two Sum gives you none of these. Use the lesson 2 hash map, or sort first, which costs O(n log n) and scrambles the original indices.
“Since the input is sorted, I’ll walk two pointers in from both ends. If the sum is too small, the left value can’t pair with anything that’s left, so I move it. That’s O(n) time and O(1) space. A hash map would be O(n) expected time, but O(n) space.”

Read/write pointers

Both pointers move left to right. r reads every element, and w marks the end of what you keep. The invariant is that v[..w] is the answer for v[..r].

fn dedup_sorted(v: &mut Vec<i32>) {
    if v.is_empty() { return; }
    let mut w = 1;                  // v[..w] = distinct values of v[..r]
    for r in 1..v.len() {
        if v[r] != v[w - 1] {
            v[w] = v[r];
            w += 1;
        }
    }
    v.truncate(w);
}
// O(n) time, O(1) extra space. Move Zeroes: same shape from w = r = 0, copy each v[r] != 0 to v[w], then zero-fill v[w..].

std already has this as Vec::dedup (“if the vector is sorted, this removes all duplicates”), and the general filter is Vec::retain, which works in place and preserves order. Mention both, then write the loop anyway, because the interviewer is grading the mechanism.

Sliding window

A window is a contiguous range s[l..r], half-open like a Rust range, and both ends only move right. With a fixed size k there is no decision to make: each step adds v[r] and subtracts v[r - k]. The maximum sum of k consecutive elements then costs O(n) time and O(1) space, against O(n·k) for re-summing every window. Negative values do no harm, because nothing has to decide when to shrink.

Variable size: expand right, shrink left

The window invariant A variable window is driven by one property that every measured window must satisfy, such as “no repeated character”, “sum ≥ target” or “at most k distinct”. On each step, r takes one element, then l moves: until the invariant holds again, or for as long as it still holds. Record the answer only at a moment when the invariant holds. Get that moment wrong and the loop is wrong.

Two shapes cover most problems, and the shrink condition is what tells them apart:

  • Longest valid window. Shrink while invalid, then record. Example: Longest Substring Without Repeating Characters.
  • Shortest valid window. Shrink while valid, recording inside the loop. Example: Minimum Size Subarray Sum.

For the first, keep a last-seen index per byte, a sibling of the lesson 2 frequency count. Rust won’t let you index a String, so work on as_bytes() after confirming with the interviewer that the input is ASCII.

fn longest_unique(s: &str) -> usize {
    let b = s.as_bytes();                       // ASCII assumed: ask first
    let mut last: [Option<usize>; 128] = [None; 128];
    let (mut l, mut best) = (0, 0);
    for (r, &c) in b.iter().enumerate() {
        if let Some(j) = last[c as usize] {
            if j >= l { l = j + 1; }            // shrink past the repeat
        }
        last[c as usize] = Some(r);
        best = best.max(r + 1 - l);             // b[l..=r] has no repeat
    }
    best
}
// O(n) time, O(1) space (a 128-entry table; O(σ) for an alphabet of size σ).
// Can you do better? Not on time: any unread byte could be the repeat that matters.

The j >= l guard matters, because the table keeps stale entries from before the window. Test on "abba": without the guard, the final a drags l backwards to 1 and you return 3 instead of 2. The second shape stores the precondition in the type, since u32 means no negatives:

fn min_len_at_least(v: &[u32], target: u64) -> usize { // target > 0
    let (mut l, mut sum, mut best) = (0, 0u64, usize::MAX);
    for r in 0..v.len() {
        sum += v[r] as u64;                     // expand right
        while sum >= target {                   // valid: measure, then try shorter
            best = best.min(r + 1 - l);
            sum -= v[l] as u64;
            l += 1;                             // shrink left
        }
    }
    if best == usize::MAX { 0 } else { best }
}
// O(n) time, O(1) space. [2, 3, 1, 2, 4, 3], target 7 → 2 (the window [4, 3]).
TimeO(n)SpaceO(1)

Why the nested while is still O(n). Count pointer moves instead of loop nesting. r moves n times, and l only moves forward, so it moves at most n times in total across all the inner loops. That gives at most 2n steps, or O(1) amortized per element. The Tech Interview Handbook puts it as “each value is only visited at most twice” (TIH, Array), and CPH §8.1 makes the same argument. This is the lesson 1 skill of reading complexity off the code, applied with a little more care.

Drive the window

You are the loop for Longest Substring Without Repeating Characters: expand when you can, shrink only when the next character would break the invariant. Illegal moves are rejected with the reason. When windows break: prefix sums

Both shrink rules rest on monotonicity: each pointer move pushes validity in one known direction. With non-negative values, adding v[r] never lowers the sum and dropping v[l] never raises it. One negative value breaks this, because dropping v[l] can raise the sum. Take [1, 2, −3, 3] with k = 3. A window that shrinks only when the sum exceeds 3 never shrinks at all (its running sums are 1, 3, 0, 3), so it counts 2 subarrays and misses [3], giving the wrong answer of 2 instead of 3. CSES splits exactly this pair of problems: Subarray Sums I has positive values and Subarray Sums II allows negatives.

The fix is a prefix-sum array of length n + 1 with p[0] = 0. Fill it with p[i + 1] = p[i] + v[i]. Then sum(v[i..j]) = p[j] − p[i] for every 0 ≤ i ≤ j ≤ n, with no special case at index 0 (USACO Guide; CPH §9.1 keeps length n and has to define sum(0, −1) = 0 by hand). For [1, 2, −3, 3], p = [0, 1, 3, 0, 3].

Prefix sum + hash map. To count subarrays with sum k, ask at each j how many earlier prefixes equal p[j] − k. That is the lesson 2 complement lookup (“have I seen target − x?”) running over prefix sums instead of values.

use std::collections::HashMap;

fn count_sum_k(v: &[i64], k: i64) -> usize {
    let mut seen: HashMap<i64, usize> = HashMap::from([(0, 1)]); // p[0]: the empty prefix
    let (mut p, mut count) = (0i64, 0);
    for &x in v {
        p += x;                                             // p is now p[j]
        count += seen.get(&(p - k)).copied().unwrap_or(0); // earlier i with p[i] = p[j] - k
        *seen.entry(p).or_insert(0) += 1;                   // insert after the lookup
    }
    count
}
// O(n) expected time (hash lookups), O(n) space. [1, 2, -3, 3], k = 3 → 3.
// Can you do better? Only with a promise: if all values are positive, a window does it in O(1) space.
TimeO(n) expectedSpaceO(n)

The time bound is expected because hash lookups are only expected O(1).

Common interview trap If you drop the {0: 1} seed, every subarray that starts at index 0 goes uncounted (on the example above the answer falls from 3 to 1). If you insert before the lookup, k = 0 starts counting empty subarrays. If you size p as n instead of n + 1, every range that starts at 0 needs a special case.

Which tool? The one-minute checklist

  • Sorted + a pair → converging pointers. O(n) time, O(1) space; a triple runs one pass per fixed element, O(n²).
  • Filter or compact in place, keeping order → read/write pointers.
  • Contiguous + a fixed length, or a constraint that moves one way as the window grows (“no repeats”, “at most k distinct”, a sum bound over non-negative values) → sliding window.
  • Contiguous + a sum target, with values that can be negative (or zero, when you count exact-sum subarrays) → prefix sums + hash map. A fixed length still means a window, negatives or not.
Why interviewers care These patterns turn O(n²) into O(n) with almost no extra memory. Follow-ups such as 3Sum and Minimum Window Substring test whether you can re-derive the invariant on the spot, not recall code.

Check your understanding

1. Minimum Size Subarray Sum (positive values, shortest subarray with sum ≥ target). After adding v[r], which loop body is correct?

2. A window loop has a for over r and an inner while whose O(1) body advances l by one; l never moves left. On n elements, what is its tight worst-case running time?

3. You seed the prefix-count map empty instead of {0: 1}. On [3, −1, 1, 3] with k = 3 it returns 2 instead of 4. Which subarrays did it miss?

4. The array is unsorted. Return the original indices of two values that sum to target. What should you reach for?
