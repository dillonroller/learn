Stacks & Queues

Stack, queue and heap questions hide one test: in what order should things come back out? The interviewer watches whether you pick the structure whose removal order fits (the newest, the oldest or the most important) and whether you know its cost. You already have the Vec cost model, and you learned to count pointer moves, not loop nesting; here that argument turns an O(n²) scan into O(n). Today’s win: Daily Temperatures with a monotonic stack in O(n), “k largest” with a size-k BinaryHeap<Reverse<_>> in O(n log k), and the right std collection named within a minute.

Stack: last in, first out

A stack returns the most recently added item first. In Rust it is a Vec: push, pop and last all work at the end, where nothing shifts. push is O(1) amortized; pop “takes O(1) time”. Cue: nesting, matching, or the most recent thing still unresolved: brackets, undo, Reverse Polish Notation. Valid Parentheses is one of the handbook’s two essential stack questions.

fn is_valid(s: &str) -> bool {
    let mut stack = Vec::new(); // closers we owe, innermost on top
    for c in s.chars() {
        match c {
            '(' => stack.push(')'),
            '[' => stack.push(']'),
            '{' => stack.push('}'),
            ')' | ']' | '}' => {
                if stack.pop() != Some(c) { return false; }
            }
            _ => {}
        }
    }
    stack.is_empty()            // an unclosed opener also fails
}
// O(n) time, O(n) space: "((((" keeps every opener.
// Can you do better? Only with one bracket type: a depth counter, O(1).
TimeO(n)SpaceO(n)

Pushing the expected closer makes each check one comparison. Min Stack pushes (value, min so far) pairs so the minimum is always on top (cp-algorithms). Every recursive call pushes a frame, which is why recursion depth costs space, and an iterative DFS is a loop around an explicit Vec.

Queue: first in, first out

A queue returns the oldest item first. In Rust that is VecDeque, “a double-ended queue implemented with a growable ring buffer”: push_back to add, pop_front to remove. The front is a head index that moves forward and wraps around, so nothing shifts; the std cost table prices insert at O(min(i, n − i)) amortized and remove at O(min(i, n − i)): O(1) at either end, amortized for pushes.

let mut q = VecDeque::from([root]);
while let Some(x) = q.pop_front() {    // oldest first
    q.extend(children(x));             // newcomers join at the back
}
// The shape of every level-order traversal and BFS.

Cue: serve in arrival order (a printer, a request buffer, a rate limiter’s timestamps) or go level by level, which is level-order traversal and BFS. At system scale, FIFO becomes a message queue.

Common interview trap A Vec as a queue. v.remove(0) shifts everything left, so each dequeue is O(n) and a full drain is O(n²) (the Vec cost model). The docs say: “If you’d like to remove elements from the beginning of the Vec, consider using VecDeque::pop_front instead.” Draining 200,000 u32s with remove(0) moves n(n − 1)/2 ≈ 2 × 10¹⁰ elements: 1.7 s on one machine and 28 s on another (Rust 1.97, -O), against about 0.2 ms with pop_front on both. In languages without a real queue the handbook says to flag this; Rust has one.

Monotonic stack: next greater element in O(n)

Daily Temperatures: for each day, how many days until a warmer one (0 if never)? Scanning forward from every day is O(n²) on a falling input. Instead keep a stack of indices of days still waiting. Invariant: their temperatures never rise from bottom to top (equal days can sit together, since only a strictly warmer day answers). Day i pops every cooler waiting day j, answers it with i − j, then pushes itself. Popping stops at the first top that is not cooler, and since nothing below it is lower, nothing below it is cooler either.

fn daily_temperatures(t: &[i32]) -> Vec<usize> {
    let mut ans = vec![0; t.len()];
    let mut stack: Vec<usize> = Vec::new(); // temps never rise bottom → top
    for i in 0..t.len() {
        while let Some(&j) = stack.last() {
            if t[j] >= t[i] { break; } // nor is anything below
            stack.pop();
            ans[j] = i - j;            // i is j’s first warmer day
        }
        stack.push(i);
    }
    ans                    // left on the stack: never warmer, 0
}
// O(n) time: each index pushed once, popped at most once.
// O(n) space (a strictly falling input never pops).
// [73, 74, 75, 71, 69, 72, 76, 73] → [1, 1, 4, 2, 1, 1, 0, 0]
TimeO(n)SpaceO(n)

Why the nested while is O(n). Count stack operations, not loop nesting. Each index is pushed once and popped at most once, so all the inner loops together pop at most n times: at most 2n operations, O(1) amortized per day. CPH §8.2 makes the same argument for nearest smaller elements: “each element is added exactly once to the stack and removed at most once”. Space is O(n) worst case, since a strictly falling input never pops.

Store indices, not values: the index gives the distance, and t[j] still gives the value. Variants: flip the comparison for next smaller; read the top before pushing for previous greater or smaller (CPH’s version); Largest Rectangle in Histogram pops a bar when a shorter one arrives, the moment both its boundaries are known. The cue: “for each element, the nearest bigger or smaller element to its left or right”.

Why interviewers care Daily Temperatures, Trapping Rain Water and Largest Rectangle in Histogram are all on the handbook’s stack list. The follow-up, “your loops are nested, so why isn’t it O(n²)?”, checks that you can make the amortized argument out loud.

“I’ll keep a stack of indices of days still waiting for a warmer day, temperatures never rising from bottom to top. Each new day pops and answers every cooler day. Each index is pushed once and popped at most once, so it’s O(n) time and O(n) space in the worst case. The brute force is O(n²).”

Stretch: the monotonic deque. For Sliding Window Maximum over a fixed-size window, keep a VecDeque of indices with falling values. Pop the back while the new value is at least as large, and pop the front once its index leaves the window; the front is the window’s maximum. Each index enters and leaves once: O(n) (CPH §8.3, cp-algorithms).

Priority queue: BinaryHeap

When the next item out should be the most important, you want a priority queue. A binary heap is a complete binary tree with the heap property: every parent is ≥ its children, so the maximum is the root (Sedgewick & Wayne §2.4). It lives level by level in a plain array: the children of i are 2i + 1 and 2i + 2, its parent is (i − 1) / 2. Push appends and swims up; pop moves the last item to the root and sinks it. Each walks one path of about log₂ n levels (algs4: at most 1 + lg n compares to insert, 2 lg n to remove the max). Only the root is ordered against everything; siblings are in no order.

The std docs give peek O(1) and pop O(log n) worst case. push is O(1) expected over random insertion orders, degrading to O(log n) amortized on ascending input, so say O(log n) in an interview. BinaryHeap::from(vec) heapifies in place in O(n).

use std::cmp::Reverse;
use std::collections::BinaryHeap;

let mut max = BinaryHeap::from(vec![5, 1, 8, 3]); // O(n) heapify
assert_eq!(max.pop(), Some(8));                   // largest first

let mut min = BinaryHeap::new();
for x in [5, 1, 8, 3] { min.push(Reverse(x)); }
assert_eq!(min.pop(), Some(Reverse(1)));     // Reverse: smallest first

// (priority, item) tuples compare field by field; ties fall to the item
let mut q = BinaryHeap::from([(2, "docs"), (9, "fix"), (9, "pager")]);
assert_eq!(q.pop(), Some((9, "pager")));       // "pager" > "fix"
Common interview trap (1) BinaryHeap “will be a max-heap”; for smallest-first, wrap items in Reverse. (2) A heap is not sorted: iter() goes “in arbitrary order”, and BinaryHeap::from(vec![5, 1, 8, 3]) iterated as [8, 3, 5, 1] on Rust 1.97. Pop repeatedly or call into_sorted_vec. (3) f64 is not Ord, so pushing one fails to compile (E0277). Use integer keys (squared distances as i64 in K Closest Points) or a newtype whose Ord calls f64::total_cmp.

Top-k: a size-k min-heap

The handbook’s cue is the mention of k: “If you see a top or lowest k being mentioned in the question, it is usually a signal that a heap can be used.” The twist: to keep the k largest, use a min-heap capped at k. Its root is the weakest of the best k so far, the first to go when something better arrives.

fn k_largest(v: &[i32], k: usize) -> Vec<i32> {
    // min-heap holding the best k seen so far
    let mut heap = BinaryHeap::with_capacity(k + 1);
    for &x in v {
        heap.push(Reverse(x));
        if heap.len() > k {
            heap.pop();            // evict the smallest of the k + 1
        }
    }
    heap.into_iter().map(|Reverse(x)| x).collect() // arbitrary order
}
// O(n log k) time, O(k) space. Can you do better? Quickselect is
// O(n) expected, but it needs all n in memory and reorders them.
TimeO(n log k)SpaceO(k)

Say the alternatives out loud. Sorting is O(n log n). A max-heap of all n is O(n + k log n) but holds every item. The size-k heap holds at most k + 1, so it works on a stream; at n = 10⁶, k = 100 each operation walks about log₂ 100 ≈ 6.6 levels, not log₂ 10⁶ ≈ 19.9. Faster still, quickselect is O(n) expected, and std’s select_nth_unstable is documented as O(n), but both need the whole slice and reorder it. Kth Largest Element is the same loop, then peek() at the root; Top K Frequent is a frequency count, then this heap over Reverse((count, item)).

Which structure? The one-minute checklist

The std guide puts it in one line each: use a Vec when “you want a stack”, a VecDeque when “you want a queue”, a BinaryHeap when “you want a priority queue”. The cues:

  • Matching, nesting, undo, most recent unresolved → stack (Vec).
  • Arrival order, level by level → queue (VecDeque).
  • For every element, the next or previous greater or smaller → monotonic stack of indices.
  • Repeatedly take the best, top or lowest k, merge k sorted → heap (BinaryHeap, Reverse for min).

Later, DFS, BFS and best-first search turn out to be one loop with a different bag: stack, queue or heap. Classify each problem; every option explains itself.

1. You push 5, 1, 8 and 3, in that order, onto a Rust BinaryHeap<i32>, then call pop() once. What comes out?

2. A queue built on a Vec dequeues with v.remove(0). What does draining n items cost in total?

3. Scores arrive as a stream of n = 10⁶ values. You must keep the k = 100 largest. Which plan fits?

4. Daily Temperatures on [30, 60, 50, 40, 55]. When day 4 (55) arrives, the stack holds days [1, 2, 3], with temps 60, 50, 40 from bottom to top. What happens?
