Binary Trees & BSTs

Tree questions look like a zoo (max depth, invert, validate, kth smallest), but the interviewer is testing one thing: can you say what your function returns for a subtree, trust the recursive call, and state O(n) time and O(h) space unprompted? You already have the pieces. The lesson 1 rule that space counts extra memory now covers the call stack. The stack and queue you just built become depth-first and level-order traversal.

The node type: Option<Box<TreeNode>>

struct TreeNode {
    val: i32,
    left: Option<Box<TreeNode>>,   // None = empty subtree
    right: Option<Box<TreeNode>>,
}
// Read-only helpers take Option<&TreeNode> and recurse on n.left.as_deref()

This is the move you made with the Formula enum in Logic lesson 2. A recursive type needs indirection to have a known size, and Box provides it (Rust Book §15.1). Option is your null, at no cost: Option<Box<T>> is guaranteed to be one pointer wide (std::option). Each parent owns its children. You need something heavier only for parent pointers or shared subtrees. Then use Rc<RefCell<…>> with Weak back-links (§15.6), or an index arena (Vec<Node> with Option<usize> children), which is often cleaner (Rust users forum). If a practice site’s stub hands you Rc<RefCell<TreeNode>>, that is the harness’s choice. On a whiteboard, choose Box.

One template: base case, then combine the children

Decide what f(subtree) returns. None is the base case. Some(n) combines f(left), f(right) and n.val. Don’t trace the recursion: assume the subcalls are right and check only the combine (lesson 8 generalizes this). It is your eval from Logic lesson 3, a post-order walk of an expression tree.

fn max_depth(node: Option<&TreeNode>) -> usize {
    match node {
        None => 0,                                      // base case
        Some(n) => 1 + max_depth(n.left.as_deref())    // combine
                        .max(max_depth(n.right.as_deref())),
    }
}

fn invert(node: &mut Option<Box<TreeNode>>) {
    if let Some(n) = node {
        std::mem::swap(&mut n.left, &mut n.right);
        invert(&mut n.left);
        invert(&mut n.right);
    }
}
// Both: O(n) time (one call per node), O(h) stack space.
// Can you do better? Not on time: every node must be read once.

In Path Sum, a node with one child is not a leaf: test “both children None” explicitly. When the parent needs something other than the answer, return two values. A diameter (longest path, in edges) through a node is left height + right height, but the parent needs the height:

// (height in nodes, best diameter in edges anywhere below)
fn diameter(node: Option<&TreeNode>) -> (usize, usize) {
    match node {
        None => (0, 0),
        Some(n) => {
            let (lh, ld) = diameter(n.left.as_deref());
            let (rh, rd) = diameter(n.right.as_deref());
            (1 + lh.max(rh), (lh + rh).max(ld).max(rd))
        }
    }
}
// O(n) time, O(h) space. Is-balanced has the same shape: return (height, ok).
“One call per node with constant work, so O(n) time. Space is the recursion stack, O(h): O(log n) if balanced, O(n) for a chain. If the tree can be very deep, I’d switch to an explicit stack.”

That last sentence is not paranoia. Measured on Linux (rustc 1.97, release build), recursive max_depth survived a 100,000-node chain on the main thread (8 MiB, the usual ulimit -s default) and overflowed the stack at 1,000,000. A spawned thread (currently 2 MiB by default) overflowed at 100,000. Even dropping the million-node chain overflowed, because a Box chain drops recursively (Too Many Lists).

Pre-, in- and post-order: where the visit sits

fn walk(node: Option<&TreeNode>, out: &mut Vec<i32>) {
    if let Some(n) = node {
        // pre-order:  out.push(n.val) here
        walk(n.left.as_deref(), out);
        // in-order:   out.push(n.val) here
        walk(n.right.as_deref(), out);
        // post-order: out.push(n.val) here
    }
}
  • Pre-order (node, left, right): act before the children. Copy or serialize a tree, or pass information down (a running sum, a depth, bounds).
  • In-order (left, node, right): on a BST, the keys come out sorted.
  • Post-order (left, right, node): the node needs its children’s answers first. Height, diameter, freeing memory and evaluating expressions all work this way.

In-order alone does not pin down the shape. Rebuilding a tree from value lists (with distinct values) takes in-order plus pre- or post-order (Tech Interview Handbook). Pre-order that also records each None does pin it down, which is one standard way to solve Serialize and Deserialize. The handbook also warns that interviewers ask for an iterative version when the recursive one comes too fast. Iterative in-order is the one to know. Dive left while pushing the path onto a Vec, pop, visit, then step right.

fn inorder_iter(root: Option<&TreeNode>) -> Vec<i32> {
    let (mut out, mut stack, mut cur) = (Vec::new(), Vec::new(), root);
    loop {
        while let Some(n) = cur {           // dive left, stacking the path
            stack.push(n);
            cur = n.left.as_deref();
        }
        let Some(n) = stack.pop() else { return out };
        out.push(n.val);                    // visit the leftmost unvisited node
        cur = n.right.as_deref();           // then its right subtree
    }
}
// O(n) time; the stack holds at most one root-to-leaf path: O(h) space.
TimeO(n)SpaceO(h)

Level order: a queue, one level per round

“By level”, “each depth” or “right side view” means breadth-first search with a VecDeque. At the start of each round the queue holds exactly one level, so snapshot q.len() and pop that many.

use std::collections::VecDeque;

fn levels(root: Option<&TreeNode>) -> Vec<Vec<i32>> {
    let mut out = Vec::new();
    let mut q: VecDeque<&TreeNode> = root.into_iter().collect();
    while !q.is_empty() {
        let mut level = Vec::with_capacity(q.len());
        for _ in 0..q.len() {                  // this level only
            let n = q.pop_front().unwrap();
            level.push(n.val);
            q.extend(n.left.as_deref());       // an Option yields 0 or 1 items
            q.extend(n.right.as_deref());
        }
        out.push(level);
    }
    out
}
// O(n) time, O(w) space for max width w: (n+1)/2 on a perfect tree.

No visited set: a tree is acyclic and every node has one parent, so each node is enqueued once. Graphs break both, which is why lesson 6 adds one.

The BST property: in-order is sorted

  
In a binary search tree, every key in a node’s left subtree is smaller than the node’s key, and every key in its right subtree is larger (Sedgewick & Wayne §3.2). That means whole subtrees, not just children. Equivalently, the in-order traversal is sorted (MIT 6.006 L6). Each comparison discards a whole subtree, which makes a BST binary search stored in pointers:

  
use std::cmp::Ordering;

fn contains(mut node: Option<&TreeNode>, x: i32) -> bool {
    while let Some(n) = node {
        node = match x.cmp(&n.val) {
            Ordering::Less    => n.left.as_deref(),
            Ordering::Greater => n.right.as_deref(),
            Ordering::Equal   => return true,
        };
    }
    false
}
// O(h) time, O(1) space: one root-to-leaf path, no recursion.

  
TimeO(h)SpaceO(1)

  
Insert follows the same path and hangs a new leaf where the search fell off, so it is O(h) too. Kth smallest is inorder_iter with a counter that returns on the k-th pop, in O(h + k) time and O(h) space. When a question says “BST”, the interviewer usually wants the ordering used to beat O(n) (TIH).


  
Validating a BST: pass the bounds down

  
Every node inherits an open interval (lo, hi) from its ancestors. Going left sets hi to the parent’s key, and going right sets lo. The bounds flow down, so this is pre-order.

  
fn is_bst(node: Option<&TreeNode>, lo: Option<i32>, hi: Option<i32>) -> bool {
    match node {
        None => true,
        Some(n) => lo.is_none_or(|l| l < n.val)
            && hi.is_none_or(|h| n.val < h)
            && is_bst(n.left.as_deref(), lo, Some(n.val))
            && is_bst(n.right.as_deref(), Some(n.val), hi),
    }
}
// is_bst(root, None, None): O(n) time, O(h) space.
// Alternative: inorder_iter, then check strictly increasing. Also O(n).

  
TimeO(n)SpaceO(h)

  

    Common interview trap
    Checking only left.val < n.val < right.val accepts 5 → left 3 → right 6. Every edge passes, but 6 sits in 5’s left subtree. The second trap is i32::MIN/i32::MAX as “no bound” sentinels. A node whose value is i32::MIN then fails lo < val. Use Option bounds or widen to i64.
  


  
Drill: valid BST?

  
Use the strict definition: left subtree smaller, right subtree larger, so a repeated key counts as a violation. For an invalid tree, say whether a direct parent–child pair is out of order, or a deeper node breaks an older ancestor’s bound.

  


  
Height decides the cost: O(h), not O(log n)

  
Height is the number of edges on the longest root-to-leaf path (max_depth counts nodes, so say which you mean). BST search, insert, min, max, floor and delete all take time proportional to the height in the worst case (algs4). The height depends on insertion order. So “BST ops are O(log n)” assumes balance. A sorted stream turns a BST into a list, and recursing on it costs O(n) call-stack space. Self-balancing trees restructure on insert to keep h = O(log n), and MIT’s framing is to design operations in O(h) and then keep h = O(log n) (6.006). This lesson skips the rotations. Know what they guarantee.

  
Rust’s std has no BST. Its ordered map is BTreeMap, a B-tree that packs many keys into each node for cache efficiency (docs), with O(log n) get, insert, remove and range (std::collections). Recognition cue: sorted iteration, ranges, min/max, or “largest key ≤ t” (map.range(..=t).next_back()) mean BTreeMap. Membership or counts alone mean a HashMap, which is expected O(1) and unordered.


  

    Why interviewers care
    Trees are the cleanest test of whether you can decompose a problem into “the answer for my subtree”, and of whether you cost recursion honestly. Saying “O(n) time, O(h) space, and h is n for a skewed tree” without prompting is the part most candidates fumble.
