Graph Traversal (BFS / DFS)

Graph questions arrive in disguise: a grid of '1's and '0's, a list of course prerequisites, a word list, a chessboard. The interviewer is testing whether you can name the vertices and edges, pick the right bag, and never process a vertex twice, and then say O(V + E) without being asked. You already own every part: lesson 4’s stack and queue are the two bags, lesson 5’s tree recursion and level order become DFS and BFS, and lesson 2’s seen-set adds the cycle protection. Today’s win: turn an edge list or a grid into a graph in Rust, then solve count the islands, fewest steps through a maze and can every course be finished? in O(V + E).

Build the graph: an adjacency list

You are rarely handed a graph object. You get n and a list of pairs, and the first three lines turn them into an adjacency list: “a vertex-indexed array of lists of the vertices connected by an edge to each vertex” (Sedgewick & Wayne §4.1).

fn build(n: usize, edges: &[(usize, usize)], directed: bool) -> Vec<Vec<usize>> {
    let mut adj = vec![Vec::new(); n];
    for &(u, v) in edges {
        adj[u].push(v);
        if !directed { adj[v].push(u); }   // undirected: store it both ways
    }
    adj
}
// O(V + E) time and space. Ids that aren't 0..n (words, airport codes):
// HashMap<&str, Vec<&str>> filled with adj.entry(u).or_default().push(v).

An adjacency matrix answers “is u–v an edge?” in O(1), but it needs Θ(V²) space however few edges exist, and listing one vertex’s neighbours costs Θ(V). A traversal over a matrix is therefore O(V²), not O(V + E) (Erickson, ch. 5). Interview graphs are sparse, so build lists. Cue: “n nodes”, “edges”, “pairs”, “connections”, “prerequisites” → build Vec<Vec<usize>> first, and say out loud whether the edges are directed.

Grids are graphs you never build

Interview graphs commonly arrive as a 2D grid: each cell is a vertex and its up, down, left and right neighbours are its edges (Tech Interview Handbook). You compute neighbours on the fly instead of building lists. An R × C grid has V = R·C and at most 2R·C edges, so any traversal is O(R·C).

const DIRS: [(isize, isize); 4] = [(-1, 0), (1, 0), (0, -1), (0, 1)];

fn neighbours(r: usize, c: usize, rows: usize, cols: usize)
    -> impl Iterator<Item = (usize, usize)> {
    DIRS.iter().filter_map(move |&(dr, dc)| {
        let nr = r.checked_add_signed(dr)?;   // None above row 0
        let nc = c.checked_add_signed(dc)?;   // None left of column 0
        (nr < rows && nc < cols).then_some((nr, nc))
    })
}
Common interview trap Writing r - 1 on a usize. At row 0 a debug build panics with “attempt to subtract with overflow”, and a --release build wraps to usize::MAX (Rust Book §3.2). After the wrap, grid.get(r - 1) quietly returns None, so the bug hides until a debug run. checked_add_signed returns None instead, and the range check covers the far edges.

The visited set: mark on discovery

Lesson 5’s level order needed no visited set, because a tree has no cycles and every node has one parent. Graphs break both guarantees. Without a record, a cycle loops forever and a vertex with three incoming edges is processed three times. Use a Vec<bool> when ids are 0..n, a Vec<Vec<bool>> for a grid, and a HashSet for strings or an unbounded board. Overwriting the cell itself (sinking '1' to '0') needs no extra memory, but ask before you mutate the input.

Mark a vertex when you push it, not when you pop it. Then each vertex enters the bag at most once. Sedgewick & Wayne and cp-algorithms both write BFS this way. Marking on pop (as TIH’s own BFS template does) is still correct, but a vertex is enqueued again by every neighbour popped before it: simulating an open 1000 × 1000 grid gives 1,998,001 pushes instead of 1,000,000, and a peak queue of 1,999 instead of 1,000.

Common interview trap “It looks like a tree, so I can skip the visited set.” The handbook warns that a tree-like diagram “could very well be a graph that allows for cycles” (TIH). Unless the problem guarantees a tree, keep the set.

DFS: count the islands

Depth-first search is tree recursion plus the visited check: follow one neighbour as deep as it goes before trying the next. Here is the recursive version on an adjacency list, counting connected components:

fn dfs(u: usize, adj: &[Vec<usize>], seen: &mut [bool]) {
    seen[u] = true;
    for &v in &adj[u] {
        if !seen[v] { dfs(v, adj, seen); }   // the only line lesson 5 didn't need
    }
}

fn count_components(adj: &[Vec<usize>]) -> usize {
    let mut seen = vec![false; adj.len()];
    let mut count = 0;
    for s in 0..adj.len() {
        if !seen[s] { count += 1; dfs(s, adj, &mut seen); }
    }
    count
}
// O(V + E) time; O(V) for seen, plus up to O(V) recursion depth.

Every vertex is marked once and every list is scanned once, which is “time proportional to the sum of their degrees” (algs4), O(V + E). The danger is depth. A recursive flood fill on an all-land 1000 × 1000 grid goes 1,000,000 frames deep, and the dfs above on a million-vertex path aborts with “has overflowed its stack” with Linux’s usual 8 MiB main-thread stack (ulimit -s 8192), in debug and release alike (lesson 8). On grids, use an explicit Vec stack:

fn num_islands(grid: &mut [Vec<u8>]) -> usize {   // b'1' land, b'0' water
    let (rows, cols) = (grid.len(), grid.first().map_or(0, Vec::len));
    let mut count = 0;
    for r in 0..rows {
        for c in 0..cols {
            if grid[r][c] != b'1' { continue; }
            count += 1;
            grid[r][c] = b'0';                     // mark on discovery: sink it
            let mut stack = vec![(r, c)];
            while let Some((r, c)) = stack.pop() {
                for (nr, nc) in neighbours(r, c, rows, cols) {
                    if grid[nr][nc] == b'1' {
                        grid[nr][nc] = b'0';
                        stack.push((nr, nc));
                    }
                }
            }
        }
    }
    count
}
// O(R·C) time: each cell is pushed at most once and checks 4 neighbours.
// O(R·C) extra space worst case, for the stack. "Can you do better?" Not on
// time: every cell must be read. Can't mutate the input? Add R·C bools.
TimeO(R·C)SpaceO(R·C)

That space bound is real: on the all-land 1000 × 1000 grid the stack peaks at 499,501 entries. One follow-up subtlety: a stack with mark-on-push reaches exactly the cells DFS would, but not in true DFS order (an exercise at the end of Erickson’s chapter 5 has you prove it is never equivalent to DFS). That matters only when you need DFS’s pre- or post-order. Backtracking is this same DFS run over a tree of choices you never build.

“Each cell is pushed at most once and checks four neighbours, so this is O(R·C) time. Extra space is O(R·C) in the worst case, for the stack. I’m sinking land in place; if I can’t mutate the input, that’s another R·C booleans. I used an explicit stack because recursion could go R·C deep.”

BFS: fewest steps

Swap the stack for a VecDeque and the search spreads in rings: every cell 1 step away, then 2, then 3. It is level order with a visited set. For any vertex v, BFS finds a path with the fewest edges (algs4: “no path from s to v has fewer edges”).

use std::collections::VecDeque;

fn min_steps(grid: &[Vec<u8>], start: (usize, usize), goal: (usize, usize)) -> Option<usize> {
    let (rows, cols) = (grid.len(), grid[0].len());
    let mut seen = vec![vec![false; cols]; rows];
    seen[start.0][start.1] = true;
    let mut q = VecDeque::from([start]);
    let mut steps = 0;
    while !q.is_empty() {
        for _ in 0..q.len() {                      // one layer: all `steps` away
            let (r, c) = q.pop_front().unwrap();
            if (r, c) == goal { return Some(steps); }
            for (nr, nc) in neighbours(r, c, rows, cols) {
                if grid[nr][nc] != b'#' && !seen[nr][nc] {
                    seen[nr][nc] = true;               // mark on discovery
                    q.push_back((nr, nc));
                }
            }
        }
        steps += 1;
    }
    None                                            // goal is walled off
}
// O(R·C) time and space. Follow-up "return the path": store each cell's
// parent when you mark it, then walk back from the goal.
TimeO(R·C)SpaceO(R·C)

Why the first discovery is the shortest. The queue only ever holds cells at distance d followed by cells at distance d + 1. Cells therefore leave in order of distance, and nothing discovered later can be closer. Snapshotting q.len() makes the layers explicit. Storing a distance per cell works too.

Multi-source BFS. Rotting Oranges asks how many minutes pass before every orange is rotten, when each rotten orange infects its neighbours once a minute. Seed the queue with every rotten cell at distance 0 and run the same loop. The answer is the largest distance reached, or −1 if some fresh orange is never reached. It is BFS from an imaginary source wired to all of them. 01 Matrix is the same move, starting from every 0.

Common interview trap “DFS finds shortest paths too.” It finds a path. In the drill below, the stack reaches the goal along 18 steps while BFS proves 8. BFS also counts edges, not costs. Once edges carry weights (minutes, prices), a plain queue gives wrong answers, and you need the priority-queue bag in the next section.

Drill: grow the BFS frontier

Each round, click every cell that joins the queue next: the open cells exactly one step further from S than the last layer. Moves are up, down, left and right. A wrong click tells you why. Coordinates are (row, col) from 0 at the top left, as in the Rust code.

One loop, three bags

Erickson calls the generic traversal whatever-first search: keep candidates in a “bag”, whose only important properties are that “we can put stuff into it and then later take stuff back out” (ch. 5). The bag decides the algorithm.

// Sketch: `bag` is any container with put/take.
bag.put(s);
while let Some(v) = bag.take() {
    if seen[v] { continue; }      // Erickson marks on removal
    seen[v] = true;
    for &w in &adj[v] { bag.put(w); }
}
BagRustAlgorithmAnswers
StackVecDFSreachability, components, flood fill
QueueVecDequeBFSfewest edges from the source
Priority queueBinaryHeap<Reverse<_>>best-first (Dijkstra)cheapest path, non-negative weights

With an O(1) bag the loop is O(V + E). A heap costs O(log E) per operation, so best-first search is O(V + E log E) (Erickson §5.6). Note where the mark goes. With a stack or queue, mark on push to keep the bag small. With a heap you must mark on removal, because a cheaper route to v can turn up after v was first seen. Dijkstra is only a preview here. TIH rates it “uncommon” in interviews and Bellman-Ford, Floyd-Warshall, Prim and Kruskal “almost never” (TIH).

Topological sort: Kahn’s algorithm

A topological order lists the vertices of a directed graph so that every edge u → v has u before v. One exists only if the graph has no cycle (cp-algorithms). Kahn’s algorithm starts from every vertex with no incoming edges. Pop one, append it, and delete its out-edges by decrementing in-degrees. A vertex whose in-degree hits 0 joins the queue. If edges remain when the queue runs dry, the graph has a cycle. In code: fewer than n vertices came out.

/// Course Schedule II. A pair (course, pre) means: take pre first.
fn find_order(n: usize, prereqs: &[(usize, usize)]) -> Option<Vec<usize>> {
    let mut adj = vec![Vec::new(); n];
    let mut indeg = vec![0usize; n];
    for &(course, pre) in prereqs {
        adj[pre].push(course);                       // edge pre → course
        indeg[course] += 1;
    }
    let mut q: VecDeque<usize> = (0..n).filter(|&v| indeg[v] == 0).collect();
    let mut order = Vec::with_capacity(n);
    while let Some(u) = q.pop_front() {
        order.push(u);
        for &v in &adj[u] {
            indeg[v] -= 1;
            if indeg[v] == 0 { q.push_back(v); }
        }
    }
    (order.len() == n).then_some(order)            // short: a cycle blocked the rest
}
// O(V + E) time and space. "Can every course be finished?" is
// find_order(n, &prereqs).is_some().
TimeO(V + E)SpaceO(V + E)
Common interview trap Getting the edge backwards. In Course Schedule the pair [a, b] means “take b before a”, so the edge is b → a. Flip it and you return a valid order for the wrong graph. Say the direction out loud before you write the loop.

What would a Google interviewer ask next? “Return the lexicographically smallest order.” Swap the VecDeque for a BinaryHeap<Reverse<usize>>. It is the bag again, now O(V log V + E). The DFS alternative (reverse post-order, with three vertex states to catch cycles) is in Erickson ch. 6. Lesson 9 fills DP tables in exactly this kind of order.

Why interviewers care The BFS loop is fifteen lines. The hard part is the modelling: deciding that words are vertices and one-letter edits are edges, then choosing the bag. The visited set is where most of the bugs live. State the cost in the problem’s own terms (“R·C cells”, “n courses plus p prerequisites”) to show that you understand O(V + E), not just recall it.

Drill: which traversal?

Name the tool before you name the code. Six prompts; a wrong pick explains itself and you can retry.

Check your understanding

1. Your BFS marks a cell visited only when it is popped (and skips cells already marked). On an open 1000 × 1000 grid, what changes compared with marking on push?

2. A graph has V = 10⁵ vertices and E = 2 × 10⁵ edges. Roughly how many basic steps does one BFS take with an adjacency matrix, and with adjacency lists?

3. Kahn’s algorithm on 6 courses outputs 4 of them, then the queue runs empty. What do you know about the other 2?

4. In a --release build, r: usize is 0 and your neighbour code computes r - 1. What happens?

Primary resource

Read Jeff Erickson, Algorithms, ch. 5 “Basic Graph Algorithms” (free PDF). Focus on “Whatever-First Search”, “Important Variants” and “Graph Reductions: Flood Fill” (§5.5–5.7). They show that one loop with a different bag gives DFS, BFS and best-first search, which is exactly the recognition skill an interview tests.
