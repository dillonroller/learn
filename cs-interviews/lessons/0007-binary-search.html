Binary Search

An interviewer asking a binary search question isn’t checking whether you know the algorithm. They are checking whether you can write it with no off-by-one, no infinite loop and no overflow, and whether you spot it in a problem with no array in sight. Lesson 1 already gave you the loop, over a half-open [lo, hi), at about 20 steps for a million elements. This lesson derives that loop from one invariant and points it at things that aren’t arrays.

Why interviewers care Binary search is easy to state and hard to write. Joshua Bloch recalls Jon Bentley asking incoming CMU PhD students to write one, and most of their versions were broken (Bloch, Google Research). Screens ask for the first x or the least capacity that works, and they watch whether your bounds are derived or guessed.

The invariant: three zones

The Big-O lesson’s loop keeps one promise at every step. Indices in [0, lo) are ruled out as too small, indices in [hi, n) are ruled out as too big, and [lo, hi) is the only place the answer can still be. Drop its Equal arm and you get the version interviews actually want, the lower bound: the first index with v[i] ≥ t. Now the zones are known false, unknown and known true, and when the unknown zone is empty, lo == hi sits on the boundary.

/// First index i with v[i] >= t, or v.len() if there is none.
fn lower_bound(v: &[i32], t: i32) -> usize {
    // Invariant: v[..lo] < t (false), v[hi..] >= t (true).
    let (mut lo, mut hi) = (0, v.len());
    while lo < hi {                         // unknown zone non-empty
        let mid = lo + (hi - lo) / 2;       // lo <= mid < hi
        if v[mid] < t { lo = mid + 1 } else { hi = mid }
    }
    lo                                      // lo == hi: the boundary
}
// O(log n) time, O(1) space. Can you do better? For membership only, a
// HashSet gives expected O(1) with O(n) space, but no “first >= t”.
TimeO(log n)SpaceO(1)
  • Start. lo = 0, hi = v.len() leaves both known zones empty, so the invariant holds before the first iteration.
  • Update. If v[mid] ≥ t, then mid and everything after it are true. hi is exclusive, so that is exactly hi = mid. Writing hi = mid - 1 would discard mid, which may be the answer. If v[mid] < t, then mid and everything before it are false: lo = mid + 1.
  • Stop. lo ≤ mid < hi, so each update at least halves hi − lo. The loop runs at most ⌈log₂(n + 1)⌉ times.

Why lo + (hi - lo) / 2, not (lo + hi) / 2

The sum lo + hi can overflow even when the midpoint fits. In 2006 Bloch described this bug in the binary search he had written for the JDK’s java.util.Arrays. It sat there for about nine years: with 2³⁰ or more elements, low + high overflows int (Bloch). By default, Rust overflow panics in debug builds and wraps in release (Rust book). We ran (lo + hi) / 2 over i32 values in [0, i32::MAX), looking for the first x ≥ 2,000,000,000. The debug build panicked with attempt to add with overflow. The release build wrapped mid negative and looped forever. This bites hardest in search on the answer, where lo and hi are values. lo + (hi - lo) / 2 is safe whenever 0 ≤ lo ≤ hi. For unsigned types there is also u64::midpoint (stable since Rust 1.85).

Common interview trap Mixing conventions. hi = mid - 1 belongs to the closed loop (while lo <= hi); in a half-open loop it skips a candidate. lo = mid under while lo < hi spins forever once hi = lo + 1, because mid rounds down to lo. Pick one invariant and derive every line from it, out loud.

In std: partition_point

The loop above is slice::partition_point, with one twist. It takes the predicate that is true on the left and returns the first index where it’s false, so lower bound is partition_point(|&x| x < t). Two calls give the run of equal elements:

let first = v.partition_point(|&x| x < t);  // first v[i] >= t
let end   = v.partition_point(|&x| x <= t); // first v[i] > t
// t fills v[first..end]; last occurrence = end - 1 if end > first

Don’t use slice::binary_search for this. With duplicates, “any one of the matches could be returned”. On [1, 3, 3, 3, 7], Rust 1.97 (the toolchain this lesson was tested with) returns Ok(3) for binary_search(&3), which is the last 3. Its Err(i) is the insertion point.

Monotone predicates: sortedness was never the point

lower_bound never needed a sorted array. It needs a monotone predicate: a yes/no question p(x) over an ordered range that reads false … false true … true. The first true is a boundary, and the same loop finds it in O(log n) evaluations of p (cp-algorithms). Sorted arrays are one source (p(i) = v[i] ≥ t). Here are others:

  • First Bad Version: p(v) = is_bad(v). There is no array, only an API.
  • Integer square root: p(m) = m·m > x, and the answer is the first true minus one. Test it as m > x / m to avoid overflow, which is equivalent for m ≥ 1, so start the range at 1. In production, use u64::isqrt (stable since 1.84).
  • Least capacity, speed or divisor: p(c) = “c is enough”, covered in the next section.

Structure is what buys the log. Without it, classical search over N items needs Θ(N) queries, and a quantum computer only reaches Θ(√N), provably optimal. A BST is the same halving frozen into pointers.

Binary search on the answer

Some problems ask for an optimum that is hard to compute but easy to check. If “c works” implies “c + 1 works”, then works(c) is a monotone predicate over the range of possible answers, and you binary search that range instead of an array.

Capacity To Ship Packages Within D Days. Packages ship in order, and no day’s load may exceed the capacity. A greedy pass checks one capacity in O(n). Below the heaviest package every capacity fails, and the total weight always works, so lo = max, hi = sum satisfies the invariant from the start.

/// Smallest x in [lo, hi) with p(x) true, or hi if there is none.
/// p must be monotone: false ... false true ... true.
fn first_true(mut lo: u64, mut hi: u64, p: impl Fn(u64) -> bool) -> u64 {
    while lo < hi {
        let mid = lo + (hi - lo) / 2;
        if p(mid) { hi = mid } else { lo = mid + 1 }
    }
    lo
}

fn ship_within_days(weights: &[u32], days: u32) -> u64 {
    let fits = |cap: u64| {                 // greedy: fill each day in order
        let (mut used, mut load) = (1, 0);
        for &w in weights {
            let w = w as u64;
            if load + w > cap { used += 1; load = 0; }
            load += w;
        }
        used <= days
    };
    let max = weights.iter().copied().max().unwrap() as u64;
    let sum = weights.iter().map(|&w| w as u64).sum();
    first_true(max, sum, fits)              // cap < max: false; cap >= sum: true
}
// O(n log S) time for total weight S, O(1) space. Can you do better?
// Start lo at max(max, ceil(S / days)): same Big-O, fewer checks.
TimeO(n log S)SpaceO(1)

Say it before you’re asked:

“Feasibility is monotone in capacity: if c ships in D days, so does c + 1. So I binary search capacities from the heaviest package to the total weight, with an O(n) greedy check each time. That’s O(n log S) time and O(1) extra space, against O(n · S) for trying every capacity.”

What would a Google interviewer ask next? Scale: 10⁵ weights of up to 10⁹ push S to 10¹⁴, past any u32 (hence u64), yet the search needs only ⌈log₂ 10¹⁴⌉ = 47 checks. Koko Eating Bananas is the same code with the check Σ ⌈pile / k⌉ ≤ h over k in [1, max pile]. In “maximize the minimum” problems the predicate runs true … true false … false, so find the first false and subtract one. The Competitive Programmer’s Handbook (§3.3) states the cost: O(log z) checks, so O(n log z) for an O(n) check.

Rotated sorted arrays

[4, 5, 6, 7, 0, 1, 2] is a sorted array of distinct values, rotated at an unknown pivot. To find the minimum, compare with the last element. Everything before the drop is greater than it, and everything from the minimum on is not, so p(i) = v[i] ≤ v[last] is monotone:

/// Index of the minimum of a non-empty rotated sorted slice of distinct values.
fn rotation_point(v: &[i32]) -> usize {
    let last = v[v.len() - 1];
    v.partition_point(|&x| x > last)       // left run > last, right run <= last
}
// O(log n) time, O(1) space.

To search in one pass, cut [lo, hi) at mid. The single drop is on one side, so the other side is sorted: the left if v[lo] ≤ v[mid], otherwise the right. Range-check the target against the sorted side’s ends. Go there if it fits, and to the other side if not.

fn search_rotated(v: &[i32], t: i32) -> Option<usize> {
    let (mut lo, mut hi) = (0, v.len());
    while lo < hi {
        let mid = lo + (hi - lo) / 2;
        if v[mid] == t { return Some(mid); }
        if v[lo] <= v[mid] {                 // v[lo..=mid] is sorted
            if v[lo] <= t && t < v[mid] { hi = mid } else { lo = mid + 1 }
        } else {                             // v[mid..hi] is sorted
            if v[mid] < t && t <= v[hi - 1] { lo = mid + 1 } else { hi = mid }
        }
    }
    None
}
// O(log n) time, O(1) space. Can you do better? Simpler, at least:
// rotation_point, then one partition_point on the run that can hold t.
TimeO(log n)SpaceO(1)

Duplicates break this. [1, 1, 2, 1, 1, 1, 1] and [1, 1, 1, 1, 2, 1, 1] read 1 at lo, mid and hi − 1, yet the 2 is on opposite sides. When the probes tie, you can only drop one end, so the worst case becomes O(n).

Recognition cues

  • Sorted input, “first / last position”, “insert position”: partition_point. The Tech Interview Handbook says sorted input should bring binary search to mind first.
  • “Minimum x such that…”, “maximize the minimum”, or a huge answer range with a cheap check: search on the answer. 10⁹ candidates cost about 30 checks.
  • Sorted but rotated: v[i] ≤ v[last], or the sorted-half rule.

And when not to. One query on unsorted data is an O(n) scan; sorting first only pays across many queries (sort as preprocessing). Pure membership is a hash table. A pair sum in a sorted array is O(n) with two pointers, not O(n log n) with n searches.

Drill: drive the search

You are the loop. Each step shows lo, hi and mid. Work out p(mid) yourself, then pick the update. Grey cells are known false, green cells are known true, and the amber outline is mid. The second mode runs the identical loop over ship capacities instead of indices.

Drill: name the predicate

The tangible skill is turning a problem statement into a monotone predicate. For each problem, pick the predicate that reads false … false true … true and gives the answer.

Check your understanding

1. With mid = lo + (hi - lo) / 2 and while lo < hi, which update can make the loop spin forever?

2. v = [1, 3, 3, 3, 7]. Which call is guaranteed to return 1, the index of the first 3?

3. Koko Eating Bananas: n = 10⁵ piles of up to 10⁹ bananas each, and checking one speed k is a single O(n) pass. What is the total time?

4. Rotated array v = [8, 9, 1, 2, 3, 5, 6], target 9. With lo = 0, hi = 7, you get mid = 3 and v[mid] = 2. What next?

Primary resource

Read cp-algorithms — Binary search, from “Search in sorted arrays” through “Binary search on the answer”. It argues from a loop invariant, as this lesson does, and covers lower/upper bound and arbitrary predicates with proofs rather than tricks. Its convention differs: sentinels l = −1 (last known false) and r = n (first known true), looping while r − l > 1, so translating its code into our half-open form is a good check that you own the invariant. It also writes (l + r) / 2, which with int indices is exactly the midpoint overflow above. Skip continuous and parallel binary search for now.
