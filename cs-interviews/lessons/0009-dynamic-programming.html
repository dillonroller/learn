Dynamic Programming

When a prompt asks how many ways, what is the minimum cost or is it possible, the interviewer is testing two things. Can you see that your brute-force recursion keeps solving the same small problem? And can you name that problem in one precise sentence? In lesson 8 you sized recursion trees, and naive fib is the O(2ⁿ) “naive recursion” row of lesson 1’s table (an upper bound; the true growth is φⁿ). Here that tree collapses to a line. In Erickson’s words, dynamic programming is “recursion without repetition” (Algorithms, ch. 3).

Overlapping subproblems: the tree repeats itself

Lesson 8’s fib(40) makes 331,160,281 calls but only ever asks about 41 distinct arguments. fib(n − k) is called F(k + 1) times: fib(n − 2) twice, fib(n − 3) three times, fib(n − 4) five times. MIT 6.006 calls a recursion a DP when “subproblem dependencies overlap (DAG, in-degree > 1)” (Lecture 15). The tree is really a small DAG whose nodes have several parents. The other ingredient, optimal substructure (answers built from smaller answers), is in the notes’ words “a property of recursion, not just dynamic programming”.

Caching also needs the answer below an argument to be independent of how you reached it. Backtracking that returns every permutation has nothing to reuse: each leaf is a distinct answer you must write out. A count, minimum or yes/no is one value per argument, so it caches.

Memoization: the same recurrence, plus a cache

Memoization (top-down) keeps the recursion as written. It checks the cache before computing and stores the result after.

fn fib(n: usize) -> u64 {
    fn go(n: usize, memo: &mut [Option<u64>]) -> u64 {
        if n < 2 { return n as u64; }
        if let Some(v) = memo[n] { return v; }      // reuse
        let v = go(n - 1, memo) + go(n - 2, memo);  // same recurrence
        memo[n] = Some(v);                          // remember
        v
    }
    go(n, &mut vec![None; n + 1])
}
// O(n) time: n + 1 states × O(1) work. O(n) space: memo + n stack frames.
// Can you do better? Fill it bottom-up, then keep only two values.
TimeO(n)SpaceO(n)

fib(40) drops from 331 million calls to 79, which is 2n − 1 (counted by running it), though the first descent still goes n frames deep. Pass the memo as &mut. A Vec<Option<_>> over small dense integers indexes in worst-case O(1). A HashMap<(usize, usize), i64> is expected O(1) plus hashing, so save it for sparse or unbounded states. Key on index tuples, not format!ed strings, and never use a global static mut.

Tabulation: fill in topological order

Draw each argument as a node, with an edge from each subproblem to every caller that reads it. That is the subproblem DAG. Tabulation (bottom-up) fills it in a topological order, so each value is ready before anything reads it. For fib that is a plain loop, dp[i] = dp[i - 1] + dp[i - 2] for i in 2..=n: O(n) time, no recursion. Erickson calls this “Fill Deliberately”.

Common interview trap “Bottom-up is faster.” Asymptotically the two are identical, because both pay states × work per state. Name the real differences: top-down skips unreachable states, while bottom-up has no recursion depth and can roll its array.

State and transition: the real work

The state is the smallest set of parameters that fixes a subproblem’s answer. The transition (recurrence) computes that answer from smaller states. If the state forgets something the future depends on, the recurrence is wrong. If it carries more than it needs, the table explodes. Erickson: “Dynamic programming is not about filling in tables. It’s about smart recursion!”

SRTBOT: six lines you can say out loud

MIT 6.006’s checklist (Lecture 15), applied to Coin Change: the fewest coins summing to amount, with unlimited supply.

  • Subproblem: dp[x] is the fewest coins summing to x, or none.
  • Relate: guess the last coin, dp[x] = 1 + min over c ≤ x of dp[x − c].
  • Topological order: increasing x, since every edge comes from a smaller sum.
  • Base case: dp[0] = 0. Original: dp[amount].
  • Time: (amount + 1) states × k coins = O(amount·k), not just “amount”.
fn coin_change(coins: &[usize], amount: usize) -> Option<usize> {
    let mut dp = vec![usize::MAX; amount + 1];  // MAX = no way to make x
    dp[0] = 0;                                   // B
    for x in 1..=amount {                        // T: increasing x
        for &c in coins {                        // R: try each last coin
            if c <= x && dp[x - c] != usize::MAX {
                dp[x] = dp[x].min(dp[x - c] + 1);
            }
        }
    }
    (dp[amount] != usize::MAX).then_some(dp[amount])  // O
}
// O(amount·k) time, O(amount) space. [1, 3, 4] gives dp = [0, 1, 2, 1, 1, 2, 2].

Top-down is the same recurrence. Option<Option<usize>> separates “not solved yet” (None) from “solved, and impossible” (Some(None)). A -1 sentinel blurs those two.

fn coin_change(coins: &[usize], amount: usize) -> Option<usize> {
    fn go(x: usize, coins: &[usize],
          memo: &mut [Option<Option<usize>>]) -> Option<usize> {
        if x == 0 { return Some(0); }
        if let Some(ans) = memo[x] { return ans; }  // outer Some: already solved
        let ans = coins.iter()
            .filter(|&&c| c <= x)
            .filter_map(|&c| go(x - c, coins, memo)) // skip unreachable x − c
            .min()
            .map(|best| best + 1);
        memo[x] = Some(ans);                         // caches “impossible” too
        ans
    }
    go(amount, coins, &mut vec![None; amount + 1])
}
// Same O(amount·k) time; O(amount) space, but up to amount frames deep.

The depth is real. With coins [1, 3, 4] this version aborts with “has overflowed its stack” at amount 100,000 on a spawned thread with the default stack, currently 2 MiB on Tier-1 platforms. The bottom-up loop handles 10⁶ (both measured with rustc 1.97, optimized).

Fill the table

Run the recurrence by hand, one cell at a time. A wrong value shows the candidates it should have compared. The second tab is a 2D state: the number of paths into a grid cell moving only right or down, which is up + left.

Greedy vs DP: why not take the biggest coin?

Greedy commits to the locally best choice and never revisits it. For coins {1, 3, 4} and amount 6 it picks 4 + 1 + 1, three coins, while 3 + 3 needs two (CPH §6.1). DP tries every last coin, so it can’t be fooled. Greedy does work for some coin systems: CPH sketches the argument for euro coins and warns that “it can be difficult to argue that a greedy algorithm works”. Erickson’s section title is “Warning: Greed is Stupid”: it “almost never works”. In an interview, find a counterexample in 30 seconds or prove the greedy choice safe. If you can do neither, use DP.

Two indices: grids and two strings

With two sequences, the state is a pair of prefixes: dp[i][j] over a[..i] and b[..j]. Longest Common Subsequence takes diagonal + 1 on a match, else max(up, left), in O(m·n) (MIT Lecture 16 uses suffixes). Edit Distance has the same shape: a match copies the diagonal, else 1 + min(up, left, diagonal) for delete, insert, replace (CPH §7.5). CPH maps n ≤ 5000 to O(n²) (§2.3): a cue for a two-index table.

Rolling arrays: keep only what the recurrence reads

List what the transition touches. Fib reads two earlier values, so two variables do: (a, b) = (b, a + b). Unique Paths reads the row above and the cell to the left, so one row does. LCS and Edit Distance also read the diagonal, which an in-place update would overwrite, so keep two rows (or one row plus the saved diagonal). Swap them with std::mem::swap and index the columns by the shorter string, for O(min(m, n)) space. The Tech Interview Handbook says “the last two values or the last two rows of the matrix will suffice”.

fn unique_paths(m: usize, n: usize) -> u64 {
    let mut row = vec![1u64; n];      // row 0: one way into each cell
    for _ in 1..m {
        for c in 1..n {
            row[c] += row[c - 1];     // up (old row[c]) + left (new row[c − 1])
        }
    }
    row[n - 1]
}
// O(m·n) time, O(n) space instead of O(m·n).

Once rows share storage, loop direction decides whether you read old or new values. Here row[c − 1] must already be new and row[c] still old, so you go left to right. In 0/1 subset sum each item is used once, so the sum loop runs right to left. Run it forward and [2, 6] “reaches” 4 by using the 2 twice. Rolling also throws away the table. If they want the actual coins or characters, keep the full table and walk back through the choices (MIT’s “parent pointers”).

Recognise it, then say it

Cues: “how many ways” (sum the choices), “minimum / maximum” (min or max them), “is it possible” (OR them), a brute force that revisits the same (index, remaining) pairs, and one number as output. “Return all” is backtracking.

Why interviewers care They grade the recurrence, not the loop. Erickson insists you first state what the subproblem means “in coherent and precise English”. That sentence (“dp[x] is the fewest coins summing to x”) lets the interviewer follow you and lets you debug a wrong cell.
“Brute force tries every last coin, which is exponential, but there are only amount + 1 distinct sums. dp[x] is the fewest coins making x: 1 + min over coins of dp[x − c], with dp[0] = 0, filled for increasing x. That’s O(amount·k) time and O(amount) space with no recursion depth. For the coins themselves I’d store the winning coin at each x and walk back.”

What would a Google interviewer ask next? “Count the ways.” Then replace min with a sum, and the loop order starts to matter. With amounts on the outside you count ordered sequences, 9 ways to make 6 from {1, 3, 4}. With coins on the outside you count combinations, 4 ways. That is Coin Change II.

Drill: define the state

Every wrong option either loses information or answers a different question.

Check your understanding

1. Coin Change with amount A and k coin values. The table has A + 1 entries. What does the bottom-up solution cost?

2. Your top-down Coin Change passes every test, then aborts with “has overflowed its stack” at amount 100,000 on a spawned thread. What is the best fix?

3. LCS of two strings with lengths m ≥ n. The interviewer wants only the length. What is the least extra space for the O(m·n) DP?

4. You memoize Edit Distance on (i, j), with 0 ≤ i ≤ m and 0 ≤ j ≤ n, and every state is reachable. Which memo do you pick?
