Sorting Algorithms

When a problem needs sorting, or would get easy if the input were sorted, the interviewer’s hidden question is: do you know what .sort() just cost you, and can you name something cheaper when the constraints allow it? You will rarely write a sort from scratch; the Tech Interview Handbook says to use your language’s default and know its cost. What gets tested is the trade-off, plus two building blocks that turn up inside other problems: merge and partition. Lesson 1 put merge sort on the O(n log n) row without saying why, and lesson 2’s space-for-time trade-off used sort_unstable as its cheap side. Today’s win: given a constraint, choose between sort, sort_unstable, select_nth_unstable, counting sort and a heap, and write merge or partition from a blank file if asked.

Merge sort: halve, recurse, merge

Split the slice in half, sort each half recursively, then merge the two sorted halves with one pointer per half: compare the heads and take the smaller. That merge is the one-pointer-per-array cousin of lesson 3’s two pointers. The classic interview twist is counting inversions, the pairs i < j with v[i] > v[j] (an exercise in algs4 §2.2). It costs one extra statement in the merge:

/// Sorts v and returns its inversion count.
fn merge_sort(v: &mut [i32], buf: &mut Vec<i32>) -> u64 {
    let n = v.len();
    if n < 2 { return 0; }
    let mid = n / 2;
    let mut inv = merge_sort(&mut v[..mid], buf);
    inv += merge_sort(&mut v[mid..], buf);
    buf.clear();
    let (mut i, mut j) = (0, mid);        // one pointer per sorted half
    while i < mid && j < n {
        if v[i] <= v[j] {                  // <= takes the left on ties: stable
            buf.push(v[i]); i += 1;
        } else {
            buf.push(v[j]); j += 1;
            inv += (mid - i) as u64;       // v[j] jumps all of v[i..mid]
        }
    }
    buf.extend_from_slice(&v[i..mid]);    // at most one tail is non-empty
    buf.extend_from_slice(&v[j..]);
    v.copy_from_slice(buf);
    inv
}
// [2, 4, 1, 3, 5] → sorted, 3 inversions.
// O(n log n) time on every input, O(n) extra.
// Can you do better? Not with comparisons (see the lower bound below).
TimeO(n log n), any inputSpaceO(n) buffer

Why n log n. Draw lesson 8’s recursion tree. The root merges n elements, its two children n/2 each, the grandchildren n/4 each: every level does n work, and halving reaches size 1 after log₂ n levels (Erickson, ch. 1, draws this tree). algs4 gives between ½ n lg n and n lg n compares; for n = 10⁶ the upper end is 19.9 million, lesson 1’s “~20,000,000”. The splits never look at the data, so every input costs Θ(n log n).

Not in place. The merge needs somewhere to write, so buf grows to n. In-place merges exist, but algs4 calls them “remarkably complicated”. Say O(n) extra (the O(log n) stack is smaller) and move on.

Stable sorts keep ties in input order

A sort is stable if elements with equal keys come out in the order they went in. It says nothing about reliability or worst cases. The <= above is what makes merge sort stable: on a tie it takes from the left half, which came first. Write < and the output is still sorted, but ties can swap, and the inversion count goes wrong too: every equal pair gets counted.

Stability matters when you sort by one key after another: records in salary order, stably sorted by department, keep salary order inside each department. The last pass is the primary key. One pass with a tuple key is often cleaner: sort_unstable_by_key(|e| (e.dept, Reverse(e.salary))) needs no stability, because the key breaks every tie you care about.

Quicksort: partition, then recurse on both sides

Pick a pivot and partition: move the smaller values left of it and the rest right, so the pivot lands at its final sorted index. Then quicksort each side. Quicksort does its work before recursing; merge sort does it after. Under pressure, write Lomuto’s partition. Erickson says Hoare’s two-pointer original “is one of the places off-by-one errors go to die”.

use std::hash::{BuildHasher, RandomState};

/// Lomuto partition around a random pivot. Returns the pivot’s final index.
fn partition(v: &mut [i32]) -> usize {
    let hi = v.len() - 1;
    // std-only random index: RandomState::new() uses random keys
    let r = RandomState::new().hash_one(hi) as usize % v.len();
    v.swap(r, hi);                  // park the pivot at the end
    let mut i = 0;                  // invariant: v[..i] < pivot <= v[i..j]
    for j in 0..hi {
        if v[j] < v[hi] { v.swap(i, j); i += 1; }
    }
    v.swap(i, hi);                  // pivot drops between the regions
    i
}

fn quicksort(v: &mut [i32]) {
    if v.len() < 2 { return; }
    let p = partition(v);
    let (left, right) = v.split_at_mut(p);
    quicksort(left);
    quicksort(&mut right[1..]);     // right[0] is the placed pivot
}
// O(n log n) expected, O(n²) worst. In place; stack O(log n) expected,
// O(n) worst. Can you do better? Recurse on the smaller side and loop on
// the larger to cap the stack at log₂ n, or call sort_unstable, which
// falls back to heapsort.
TimeO(n log n) expected, O(n²) worstSpaceO(log n) expected stack

Why the pivot is random. With a fixed last-element pivot, sorted input makes every pivot the maximum: partitions shrink by one, for n(n − 1)/2 comparisons (1,999,000 at n = 2,000; we counted) and recursion n deep. algs4 §2.3: “~N²/2 compares in the worst case, but random shuffling protects against this case.” With a random pivot, the values ranked i < j are compared only if one of them is the first pivot drawn from ranks i through j: probability 2/(j − i + 1). Summing over all pairs by linearity of expectation gives at most 2n ln n ≈ 1.39 n log₂ n expected comparisons (CMU 15-451, §3.4) for every input, because the coin flips are the algorithm’s own.

Not stable, and duplicates hurt. Swaps jump elements past their equals, so quicksort is not stable. On all-equal input nothing is < the pivot, so Lomuto splits 0 / n − 1 however you pick it: quadratic again (also 1,999,000 comparisons at n = 2,000). The fix is a three-way partition into <, = and > regions: Dijkstra’s Dutch National Flag problem. algs4 states as a proposition that quicksort with 3-way partitioning is entropy-optimal: the more duplicates, the faster it gets. LeetCode’s Sort Colors is exactly that partition on the values 0, 1, 2.

Common interview trap “Quicksort is O(n log n).” That is the expected cost with a random pivot. Say “expected”, then name the worst case before you are asked: O(n²) time and O(n) stack, from sorted input with a fixed pivot or from many duplicates with a two-way partition.

Quickselect: partition, then keep one side

After a partition the pivot sits at its sorted index p. If you want only the element at sorted index k, either k = p and you are done, or the answer is on the one side that contains k. Drop the other side. That is Hoare’s quickselect, “one-armed quicksort” (Erickson, ch. 1), and it needs no recursion:

use std::cmp::Ordering;

/// The k-th smallest value (0-based). Reorders v.
fn quickselect(v: &mut [i32], k: usize) -> i32 {
    let (mut lo, mut hi) = (0, v.len());
    loop {
        let p = lo + partition(&mut v[lo..hi]);    // random pivot, as above
        match k.cmp(&p) {
            Ordering::Equal   => return v[p],
            Ordering::Less    => hi = p,
            Ordering::Greater => lo = p + 1,
        }
    }
}
// O(n) expected, O(n²) worst; O(1) extra. Can you do better? In Rust,
// *v.select_nth_unstable(n - k).1 is the k-th largest (1-based k),
// and O(n) in the worst case.
TimeO(n) expectedSpaceO(1) extra

If every pivot halved the range, the work would be n + n/2 + n/4 + … < 2n. With random pivots the larger side averages ¾ of the range, and the expected count stays below 4n comparisons (CMU 15-451, Lecture 4). In Rust you call select_nth_unstable, documented as in place and O(n). In the Rust 1.99 docs (current stable as of October 2026) it is an introselect whose median-of-medians fallback “guarantees linear runtime for all inputs”. On 10⁷ random i32s (rustc 1.97, -O, our test machine) it took about 20 ms; sort_unstable took about 200 ms. Say the comparison with lesson 4’s size-k heap out loud:

“Sorting would be O(n log n). A size-k min-heap is O(n log k) time and O(k) space, and it works on a stream. Since the whole array is in memory and I may reorder it, I’ll use quickselect: O(n) expected, O(1) extra. In Rust that’s select_nth_unstable, which is linear even in the worst case. If I mustn’t mutate the input, the clone costs O(n) space.”

The n log n wall

A sort that learns about its input only by comparing pairs can be drawn as a decision tree. Each node asks “a < b?”, and each leaf is one output order. All n! orders must be leaves, and a binary tree with n! leaves has height at least log₂(n!) ≈ n log₂ n − 1.44n. So some input forces about n log₂ n comparisons (CPH §3.1). algs4 states it as “No compare-based sorting algorithm can guarantee to sort N items with fewer than lg(N!) ~ N lg N compares”. For n = 10⁶ the floor is 18.5 million comparisons. Merge sort’s worst case, at most 19.9 million, is within 8% of it, which is why algs4 calls mergesort asymptotically optimal.

The wall stands only for comparison sorts, and interviewers love the way round it.

Counting sort: index by the key instead of comparing

When keys are small integers in a known range of size k, count each value, then write the values back in order. That is O(n + k) time and O(k) extra space, and no two elements are ever compared, so the bound does not apply (CPH §3.1). The handbook’s cue is numbers “where you know the range of values beforehand”.

fn sort_ages(ages: &mut [u8]) {   // every age is in 0..=120
    let mut count = [0usize; 121];
    for &a in ages.iter() { count[a as usize] += 1; }
    let mut i = 0;
    for (age, &c) in count.iter().enumerate() {
        ages[i..i + c].fill(age as u8);
        i += c;
    }
}
// O(n + k) time, O(k) extra, k = 121.
// Can you do better? Not asymptotically: you must read every age.
TimeO(n + k)SpaceO(k)

On 10⁸ random ages (same machine) this took about 60 ms; sort_unstable took about 1.1 s. To move whole records, turn the counts into start offsets with a prefix sum and drop each record into its key’s next slot. That version is stable, and radix sort repeats it once per digit. When k is huge (any i32, any timestamp) the count array is the problem: 2³² usize counters are 32 GiB.

Sort as preprocessing: “can I sort this?”

Sorting costs O(n log n) once and buys order. Neighbours become meaningful, pointers can move in one direction, and binary search works. When the brute force is O(n²) and nothing needs the original order, ask out loud whether sorting first helps.

  • Intervals: sort by start, which the interval cheatsheet calls crucial for Merge Intervals.
  • Pairs or triples hitting a target in O(1) extra space: sort, then converging pointers. 3Sum drops from O(n³) to O(n²).
  • Many queries against one dataset: sort once, then a lower bound per query, O((n + q) log n). For a single query, a linear scan wins.
  • Duplicates with tight memory: sort in place and compare neighbours, O(n log n) time and O(1) extra, against the seen-set’s O(n) expected time and O(n) space. Sorting scrambles indices; carry them if needed.
fn merge(mut iv: Vec<[i32; 2]>) -> Vec<[i32; 2]> {
    iv.sort_unstable_by_key(|r| r[0]);    // the whole trick
    let mut out: Vec<[i32; 2]> = Vec::with_capacity(iv.len());
    for r in iv {
        match out.last_mut() {
            // overlaps the last block (touching counts): extend it
            Some(last) if r[0] <= last[1] => last[1] = last[1].max(r[1]),
            _ => out.push(r),
        }
    }
    out
}
// [[1,3],[8,10],[2,6],[15,18]] → [[1,6],[8,10],[15,18]]
// O(n log n) time, O(n) for the output.
TimeO(n log n)SpaceO(n) output; sort in place
Why interviewers care Merge Intervals, Meeting Rooms II and Kth Largest sit on the handbook’s practice lists, and like 3Sum each is “sort (or partition), then something simple”. The grade is for seeing the sort, stating its cost, and knowing whether you could do without it. Ask whether [1, 2] and [2, 3] overlap before writing <=.
