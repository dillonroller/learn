System Design Fundamentals

A system design round has no compiler and no test cases, so the interviewer’s hidden question changes: can you turn a vague product ask into numbers, and justify every box you draw by the bottleneck it removes? There is no single right answer; what gets graded is trade-off reasoning and how you drive the conversation. You already own the parts. Lesson 1’s orders of magnitude become QPS and latency estimates, the hash table becomes a cache and a shard map, and the FIFO queue becomes a message queue between machines. Today’s win: walk “Design a URL shortener” through requirements, estimates, API, high-level design and deep dives, naming the building block each bottleneck calls for. That is the high-level fluency your mission asks for; the full deep dive is a later topic.

The framework: requirements before boxes

Hello Interview’s delivery framework budgets the round like this. You drive it and state each assumption out loud.

  1. Requirements (~5 min). Functional: about three “users should be able to…” statements. Non-functional: latency, availability, scale, consistency, with numbers where you can.
  2. Core entities (~2 min). The nouns your API trades in. Start small and add as you go.
  3. API (~5 min). One endpoint per functional requirement. “Default to REST unless you have a specific reason not to.”
  4. High-level design (~10–15 min). The simplest boxes and arrows that serve every endpoint.
  5. Deep dives (~10 min). Return to the non-functional requirements and fix the bottlenecks they expose. The more senior you are, the more you lead.

Estimation is not a ritual step: the guide says to calculate “only if they will directly influence your design”. For a read-heavy service they decide cache and sharding, so you do them. Applied to the URL shortener:

  • Functional: create a short code for a long URL; visiting the code redirects to the long URL.
  • Non-functional: fast redirects (Hello Interview’s Bitly breakdown sets under 100 ms), high availability, globally unique codes, far more reads than writes.
  • Entity: ShortUrl { code, long_url, created_at }.
  • API: POST /urls {long_url} → {code} and GET /{code} → 302. The breakdown prefers 302 over 301 so browsers don’t cache the redirect and every click still reaches you.
Why interviewers care With no test suite, your process is the signal. Assumptions said out loud let the interviewer correct you in minute three, not grade a design for a problem they never posed.

Back-of-the-envelope: numbers pick the boxes

Round hard. You want the order of magnitude, the same move as dropping constants in Big-O. Three conversions cover most rounds:

  • QPS = per-day count ÷ 10⁵. A day is 86,400 s; the 16% error never changes a design.
  • Peak = average × a factor you say out loud, such as “assume 3× at peak”.
  • Storage = records per day × bytes per record × 365 × years.

For latency, quote Jeff Dean’s “Numbers Everyone Should Know” (LADIS 2009 keynote; SSD row from the widely shared table built on it). They are 2009-era figures: orders of magnitude, not specs.

The bigger win is throughput: Hello Interview’s core concepts puts a single Redis instance at “hundreds of thousands of operations per second” against “tens of thousands of queries per second” for a well-tuned database.

Estimate it: the URL shortener

Given: 100M daily active users. 1 in 10 creates one link a day. Each link gets 100 redirects (100:1 reads to writes). About 500 bytes per stored link, kept 5 years. Any answer within ±50% counts; 10k and 1e4 both parse.

Scale out: load balancer + stateless servers

Vertical scaling buys a bigger machine. Horizontal scaling runs N identical app servers behind a load balancer, so capacity means adding a box. It only works if the servers are stateless: the Twelve-Factor App says processes are “stateless and share-nothing”, persistent data lives in “a stateful backing service”, and sticky sessions “should never be used or relied upon”. Hello Interview distinguishes L7 balancers (route on the HTTP request) from L4 (route TCP connections; typically what long-lived WebSockets need). At Google’s scale DNS balancing comes first and a virtual-IP balancer second (SRE book, ch. 19).

Cue: one app server pegged, or “sessions live in server memory”. Move the state out, then add servers.

Caching: a hash map in front of the database

A cache is the hash table moved into RAM on its own servers (Redis, Memcached). The default pattern is cache-aside: “On a read, check the cache first. If the data is there, return it. If not, query the database, store the result in the cache with a TTL, and return it” (Hello Interview).

use std::{collections::HashMap, time::{Duration, Instant}};

const TTL: Duration = Duration::from_secs(300);

struct Redirects {
    cache: HashMap<String, (String, Instant)>, // stands in for Redis
    db: HashMap<String, String>,               // stands in for the database
}

impl Redirects {
    /// Cache-aside read: try the cache, fall back to the DB, fill the cache.
    fn long_url(&mut self, code: &str) -> Option<String> {
        if let Some((url, expires)) = self.cache.get(code) {
            if Instant::now() < *expires { return Some(url.clone()); } // hit
        }
        let url = self.db.get(code)?.clone();                          // miss
        self.cache.insert(code.to_owned(), (url.clone(), Instant::now() + TTL));
        Some(url)
    }
}
// A hit costs one hash lookup and no database work; a miss costs a DB read plus a cache write.
// Can you do better? Delete the key on every write, so readers never wait out the TTL.
TimeO(1) expected per lookupSpacebounded by eviction

Two knobs. The TTL bounds staleness. Eviction bounds memory: a full Redis drops keys by policy, and the Redis docs call allkeys-lru “a good default” when a subset of keys gets most of the traffic. That eviction rule is the LRU Cache coding question: a hash map plus a doubly linked list.

Caching pays only when reads are skewed: with reads spread evenly, a cache holding 5% of rows serves about 5% of reads. Short links suit it: viral links are a tiny hot set, and a mapping never changes, so a long TTL costs nothing.

Common interview trap “Add a cache and you’re done.” Name what remains. Invalidation: delete on write, or accept staleness up to the TTL. Cold start: an empty cache sends every read to the database. Stampede: a hot key expires and concurrent misses pile onto the database; fix with a refill lock (one request refills, the rest wait or get the old value), and add random jitter to TTLs so many keys don’t expire together.

Replication vs sharding

Replication copies the whole dataset to more machines. Reads scale and a replica can replace a dead primary, but writes still funnel through one primary, and copies lag. PostgreSQL streaming replication is asynchronous by default, with “a small delay” before a commit is visible on a standby, “typically under one second”. A user who reads a replica right after writing may not see their own write.

Sharding (partitioning) splits the data by key so each machine holds one slice. It scales writes and storage, at the price of cross-shard queries and rebalancing. Order matters. Hello Interview: “The biggest mistake with sharding is doing it too early.” Do the capacity math first: “If you’re at 10K writes per second and 100GB of data, you don’t need sharding yet,” and a single Postgres instance “handles a few terabytes comfortably”.

For the shortener, ~100 writes/s is nowhere near that, and storage reaches ~9 TB only in year 5. So: cache and replicas now; shard by code when storage, not traffic, forces it. Each lookup by code hits a B-tree index (the usual default), a balanced sorted tree, so the height argument gives O(log n).

Consistent hashing: add a node, move a sliver

The obvious shard map is hash(key) % N. Change N and almost every key moves: from 10 nodes to 11, a key stays only when h % 10 == h % 11, 1 key in 11, so 10/11 ≈ 91% move. For a cache that is a miss storm; for a database, a near-total migration.

Consistent hashing, as Amazon’s Dynamo uses it, hashes nodes and keys onto the same ring and gives each key to the first node clockwise. A new node takes only the arc just before it: “departure or arrival of a node only affects its immediate neighbors”. One random position per node gives uneven arcs, so Dynamo gives each node many positions, virtual nodes. In Rust the ring is a BTreeMap, and “first node clockwise” is a lower bound:

use std::collections::BTreeMap;
use std::hash::{DefaultHasher, Hash, Hasher};

fn h<T: Hash>(x: T) -> u64 {
    let mut s = DefaultHasher::new();
    x.hash(&mut s);
    s.finish()
}

/// Consistent-hash ring: position on the ring -> node id.
struct Ring { ring: BTreeMap<u64, u32> }

impl Ring {
    fn new(nodes: u32, vnodes: u32) -> Self {
        let ring = (0..nodes)
            .flat_map(|n| (0..vnodes).map(move |v| (h((n, v)), n)))
            .collect();
        Ring { ring }
    }
    /// The first node clockwise from the key, wrapping past the top.
    fn node(&self, key: u64) -> u32 {
        let p = h(key);
        let (_, &n) = self.ring.range(p..).next()
            .or_else(|| self.ring.iter().next())
            .expect("empty ring");
        n
    }
}

// Count keys 0..1_000_000 whose owner differs between 10 and 11 nodes (100 vnodes each):
// hash % N moves 90.9%, the ring moves 9.4% (ideal 1/11 = 9.1%). O(log(N·V)) per lookup, O(N·V) space.
// Can you do better? Jump consistent hash needs no ring at all, but its buckets
// must be numbered 0..N, so nodes can only leave from the end.
TimeO(log(N·V)) per lookupSpaceO(N·V) ring

BTreeMap::range is O(log n) (std cost table); jump hash is Lamping & Veach (2014). Why vnodes: on the same million keys (Rust 1.97’s DefaultHasher), one position per node left the busiest of 10 nodes with 24.4% of keys and the idlest with 0.7%; 100 vnodes each narrowed that to 11.9% and 8.5%.

Message queues: decouple now, finish later

A message queue is the FIFO stretched across machines. Producers enqueue and return at once; workers drain at their own pace. Microsoft’s Queue-Based Load Leveling pattern says the queue “acts as a buffer”, so you size workers “for an average load rather than the peak load”. The same page lists the costs: a poor fit when “the caller requires a low-latency, synchronous response”; if producers outpace consumers, “the queue continues to grow and latency increases”; and most queues deliver at least once, so consumers must be idempotent (processing twice leaves the same result; SQS says the same). Skip event ids already in a seen-set kept in the database, or make the write an upsert.

In the shortener, click analytics go here: the redirect enqueues {code, timestamp, event_id} and returns its 302 at once. A queue doesn’t make work faster; it moves work off the request path and smooths spikes, paid for in latency and duplicates. Brokered queues versus brokerless pub/sub is in the robotics track’s pub/sub section.

CAP, stated honestly

Networks delay and drop messages. Kleppmann: partition tolerance “basically means that you’re communicating over an asynchronous network that may delay or drop messages… you don’t really have any choice in this matter” (“Please stop calling databases CP or AP”). So the real question is what a replica cut off by a partition does with a request: refuse or wait, keeping consistency (CAP’s C is linearizability: every read sees the latest write), or answer with what it has, keeping availability, possibly stale.

Eric Brewer, who stated the conjecture, wrote that “the ‘2 of 3’ formulation was always misleading”. CAP “prohibits only a tiny part of the design space: perfect availability and consistency in the presence of partitions” (CAP Twelve Years Later). With no partition you can have both, and Kleppmann adds that CP/AP labels oversimplify real databases. Dynamo chose availability, “an eventually consistent data store”, because “Add to Cart” must never be “forgotten or rejected”; divergent carts are reconciled later.

Choose per operation, not per system. Say it like this:

“Redirects favour availability. A mapping never changes once created, so a lagging replica can at worst miss a link made a second ago. Code allocation favours consistency: if a server can’t reach the ID counter during a partition, it fails the create rather than risk handing out a duplicate. With no partition we get both.”

Drill: name the building block

Each scenario has one bottleneck. Pick the block that removes it; a wrong pick tells you why it misses.

Check your understanding

1. A photo app expects 50 million uploads a day, spread across the day. Roughly what average write QPS do you say out loud?

2. Your consistent-hash ring is stored as a sorted Vec<(u64, NodeId)> of positions. Which lookup finds a key’s node, and at what cost?

3. A network partition cuts replica R off from the rest of the cluster. A client asks R for the latest value of a key. Under CAP, what are R’s honest options?

4. Your click-count worker reads from an at-least-once queue and does count += 1 per message. After a broker restart the counts drift high. What fixes it?
