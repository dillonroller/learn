DDS, Topics, and Where ROS2 Fits

You've already used this. Every script that talked to the Go2 in this project has been doing pub/sub messaging over DDS — this lesson just names what you were already doing.

Code you've already run Open scripts/run_stand_mission.py and look near the top of main(): 
ChannelFactoryInitialize(domain_id, interface)

pub = ChannelPublisher("rt/lowcmd", LowCmd_)
pub.Init()

sub = ChannelSubscriber("rt/lowstate", LowState_)
sub.Init(handler, 10)

That's the whole pattern this lesson explains: a publisher sending on a named channel, a subscriber listening on one, and a domain scoping who can hear whom. The earlier lesson on coordinate frames was about what one telemetry sample means. This one is about how that sample physically gets from the robot into your script's handler callback at all.

1. Publish/subscribe, the pattern underneath

If you've used any event bus, message queue, or observer pattern, the shape will feel familiar — with one important difference. A publisher sends messages tagged with a channel name (a topic), like rt/lowcmd. A subscriber declares "I want messages on that topic." Neither one holds a reference to the other, calls the other directly, or even needs to know the other exists. They only agree on the topic name and the message type.

The difference from something like a typical message-broker queue (Kafka, RabbitMQ, SQS): DDS has no central broker to route through. Every participant on the network runs its own copy of the DDS stack and discovers publishers/subscribers directly, peer-to-peer. There's no single server whose downtime takes the whole system out — which matters for a robot, where "the message broker is down" is not an acceptable failure mode mid-mission.

2. Domains: the isolation boundary

Before any of that discovery happens, every participant picks a domain id — in run_stand_mission.py, that's the domain_id argument, defaulting to 1. Concretely, in the DDS implementation this project uses (Eclipse Cyclone DDS, the same one unitree_sdk2py is built on), each domain id maps to its own UDP port range for discovery traffic — Cyclone's own docs put it plainly: "this mapping of domain ids to UDP/IP port numbers ensures that accidental cross-domain communication is impossible with the default mapping." Two processes on domain 1 and domain 2 aren't just "not subscribed to each other" — they never even discover that the other exists. This is why your simulated Go2 and someone else's, on the same Wi-Fi, don't interfere: different domain ids, invisible to each other by construction, not by convention.

4. Where ROS2 fits on top of this

unitree_sdk2py talks raw DDS — no ROS2 involved yet. ROS2 is a separate layer that happens to use DDS as its own default transport: per ROS2's own design documentation, "ROS on DDS", DDS and its wire protocol (RTPS) were adopted as the underlying communication standard for ROS2 itself. So a ROS2 "topic" is the exact same publish/subscribe idea you just used above, plus a layer of conventions on top: named nodes (one process, one job — a driver, a planner, a logger), standardized message types, and two extra communication shapes for things that aren't a continuous stream — services (request/response, e.g. "reset the map") and actions (long-running and cancelable, e.g. "navigate to this waypoint").

unitree_ros2 is the bridge: it takes the same DDS traffic you just published/subscribed to directly, and re-exposes it as proper ROS2 topics/nodes so standard tooling (RViz, ros2 bag, nav2) can point at a Unitree robot without knowing anything Unitree-specific. Nothing about the wire format changes — you're just adding a naming/tooling convention on top of the same publish/subscribe mechanism.

Primary resource "Understanding ROS 2 topics" — official ROS 2 documentation. Short, hands-on, and uses the exact vocabulary (nodes, topics, publishers, subscribers) this lesson used above — worth doing the CLI walkthrough once you have ROS2 installed alongside unitree_ros2.
