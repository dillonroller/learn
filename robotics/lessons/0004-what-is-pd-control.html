What Kp and Kd Actually Do

Zero-background rundown of proportional–derivative control, using a real Go2 stand-up failure as the running example — and a toy simulator that reproduces it almost exactly.

The real failure that started this On 2026-08-24, a mission script commanded a simulated Unitree Go2 to ramp all 12 joints to a standing pose over 3 seconds, then hold. It defined its own success bar: every joint within 0.05 rad of target. It missed — the rear-right hip joint settled 0.181 rad short and stayed there. The IMU said the robot looked nearly upright. The mission still failed its own test. This is real captured mission-report output, not a made-up example: 
{
  "step": "ramp_to_stand_pose", "status": "failed", "max_joint_error": 0.18120715
},
{
  "step": "hold_stand_pose", "status": "failed", "max_joint_error": 0.16855961
}

By the end of this lesson you'll know why that 0.181 rad number showed up, and roughly what has to change to make it go away. This lesson is about building the intuition from nothing — actually editing the script yourself is the natural next step once you're confident here.

1. Feedback control, the idea underneath everything

Every joint on the Go2 is driven by a controller running roughly 500 times a second, doing the same simple thing each tick: look at where the joint is, compare it to where it's supposed to be, and push proportionally to close that gap. That's the entire idea of feedback control — no different in spirit from a thermostat, which measures room temperature, compares it to the setting, and turns the heat up or down accordingly.

Define the error as e = desired − actual. Every controller in this lesson is just a different way of turning e (and how fast e is changing) into an output.

2. The P term: push proportional to how wrong you are

The simplest possible controller: output a force proportional to the error. Big gap, big push. Small gap, small push. Zero gap, no push. The constant of proportionality is called Kp (position gain):

push = Kp * (q_desired - q_actual)

This behaves exactly like a spring pulling the joint toward its target — the higher the Kp, the stiffer the spring. That already explains two things that go wrong:

  • It can overshoot and oscillate. A spring pulled and released doesn't stop at the target — it swings past, gets pulled back the other way, and rings back and forth. A P-only controller can do the same.
  • It droops under a steady load. If something is constantly pushing back — like gravity pulling a leg down — the joint settles wherever the spring's pull exactly balances that load, which is short of the actual target. More on this in §4, because it's exactly what happened to the Go2's hip joint.

3. The D term: push against how fast things are changing

To stop the ringing, add a second term that responds not to the error itself, but to velocity — how fast the joint is already moving. This is Kd (velocity gain), and it acts like a shock absorber: the faster the joint moves, the harder Kd pushes back against that motion, dissipating energy instead of storing it like a spring does.

push = Kp * (q_desired - q_actual) + Kd * (0 - q_velocity)

Put the spring (Kp) and the shock absorber (Kd) together and you have a PD controller — exactly what's running on every one of the Go2's 12 joints. Too little Kd and it rings like an undamped spring; too much and it becomes sluggish, since it's now fighting its own motion even when that motion is headed the right way.

4. Try it yourself

Below is a toy version of one Go2 leg joint, obeying the exact same equation the robot's motor firmware runs. It starts at 0 rad and gets commanded to step straight to 0.67 rad — the thigh joint's angle in the real standing pose. A constant load (gravity, fighting to pull the leg back down) is always pushing back with about 10.9 N·m — sized so this toy reproduces the real 0.181 rad droop almost exactly at the real gains. It is not a physically exact model of the Go2's leg; it's built to make the numbers line up so the intuition transfers.

Try, in order:

  1. Leave Kp and Kd at 0 and press the button. Nothing holds the joint up — pure gravity.
  2. Raise Kp alone (Kd still 0). It moves toward target, but rings — and settles short.
  3. Add some Kd. The ringing damps out. It still settles short.
  4. Set Kp = 60, Kd = 5 — the Go2's actual gains. Compare the settled error to 0.181 rad.
  5. Now tick "add gravity feedforward" at Kp=60, Kd=5. Watch the steady error disappear.
The key insight this demo is built to show Raising Kp shrinks the steady droop but never zeroes it — there's always some leftover error needed to generate enough spring force to balance the load. The only way to fully cancel a known, steady load is to add it directly as a feedforward term (tau_ff) instead of asking the position error to supply it indirectly. That's the fourth term in the full control law: 
tau = Kp*(q_des - q) + Kd*(dq_des - dq) + tau_ff
This is exactly the field layout in the Go2's motor_cmd struct (q, dq, kp, kd, tau) — see Ben Katz's MIT thesis, which is where this convention originates for this whole family of legged-robot actuators.

5. Why the real robot used Kp=60, Kd=5 at all

These aren't arbitrary. They're copied — correctly — from Unitree's own official go2_stand_example.cpp. That makes them a reasonable generic starting point, not gains anyone tuned for this specific ramp-then-hold mission and its 0.05 rad tolerance. Copying a working example is a completely normal first move — the goal is to be able to look at the result, understand why it fell short, and adjust it with reasons instead of guesses.

Update — the real script has since moved past pure PD This lesson was written against the honest failure captured above. Since then, the mission script gained a third term: a per-joint integral gain (KI=6), fed through the same tau feedforward field this lesson's simulator uses. It's the other classic fix for steady-state droop — instead of you supplying the load torque directly (what the "add feedforward" toggle above does), the integral term accumulates the error over time and discovers whatever feedforward torque cancels the load on its own, with no need to know it in advance. Two things from its tuning history are worth knowing:
  • An untuned integral (KI=20, active during the ramp too) made things worse than no integral at all — 0.29 rad error, oscillating. Partly because ramp tracking-lag got integrated as if it were a real disturbance, partly because standing on four legs is a coupled whole-body balance problem, not 12 independent joint loops — a preview of Lesson 6.
  • An intermediate KI=9 converged cleanly on its first run (0.042 rad) — then oscillated and failed on an identical second run. One successful run wasn't evidence it worked. The final KI=6 was verified over 3 consecutive fresh runs before being accepted. That distinction — a single good run vs. a verified, reproducible one — is exactly what Lesson 7 (the sim-to-real gap) is about.
Final result: mission completed, max joint error ≈0.028 rad over 3 consecutive fresh-sim runs, comfortably under the 0.05 rad tolerance.

Practice before next lesson

Here is the actual per-joint command loop from the reference project's mission script, trimmed to the part that matters — it's exactly the tau = Kp*(q_des - q) + Kd*(dq_des - dq) + tau_ff law from §4, with the integral-fed tau_ff from the update box above:

def apply_command(target_pos):
    for i in range(12):
        error = target_pos[i] - motor_state[i].q
        integral[i] = clamp(integral[i] + error * CONTROL_DT, +/-INTEGRAL_CLAMP)
        tau_ff = clamp(KI * integral[i], +/-TAU_LIMIT)
        motor_cmd[i].q   = target_pos[i]   # position target
        motor_cmd[i].kp  = KP               # 60.0
        motor_cmd[i].kd  = KD               # 5.0
        motor_cmd[i].tau = tau_ff           # 0 in the original PD-only version

Take these real captured numbers (Kp=60, Kd=5, 0.181 rad droop on the rear-right hip) and, if you have unitree_mujoco running, try the same experiment yourself against a script like this one — raise Kp, then try adding a fixed feedforward term instead of the integral — and see how the error changes. Compare it against what the update box above says actually shipped.
